# 03 — What DollsMP can be reused for *Queen's Domain* co-op

**Purpose.** Audit the working *Dolls Nest* co-op mod at `G:\Freespace\dollsMP` and decide,
component by component, what carries over to a 2-player co-op mod for **Queen's Domain**
(UE 4.27, first-person, single-player), which must sync quest progression, quest items,
loot, dialogue, enemy state and movement.

**Evidence base.** Everything below was read in the repository: `README.md`,
`HANDOFF.md` (1,132 lines), `HANDOFF_claude1.md` (344 lines), `Cargo.toml`, every crate
under `crates/`, `mod/lua/scripts/main.lua` (7,699 lines), `mod/src/dllmain.cpp`,
`mod/cpp/dollsmp_net.cpp`, `mod/native/src/` (74,181 lines across `proxy.cpp`, 47 headers,
7 test `.cpp`s),
`reference/sdk/RUNTIME-CAPABILITIES.md`, `docs/sync/_PROTOCOL.md`, `docs/sync/12-*`,
`docs/sync/20-*`, `docs/sync/83-*`, `docs/sync/ue4ss-removal/PLAN.md`, and `tools/`.

**Read this first — the README is stale.** `README.md` describes the *first* architecture
(UE4SS + Lua + file bridge) and says "in-game puppet rendering … not finished". That is
two months out of date. `HANDOFF.md` and `mod/native/` show the shipped mod is a **native
`dxgi.dll`/`version.dll` proxy with no UE4SS and no Lua**, and the puppet, world sync,
quests, bosses, movers and dialogue were all built. The single most important reuse fact is
therefore: **the valuable asset is the native-module architecture and its 47 design-record
headers, not the Lua client the README advertises.**

## A. Architecture recap — how the mod actually works, end to end

### A.0 Two generations (know which one you are reading)

| Gen | In-game component | Status | Where |
|---|---|---|---|
| 1 | `UE4SS.dll` + `Mods/DollsMP/Scripts/main.lua` | **dead** — removed from every instance | `mod/lua/`, `mod/src/`, `mod/cpp/` |
| 2 | `dxgi.dll` / `version.dll` proxy (C++), Rust staticlib linked in | **the shipping mod** | `mod/native/`, `crates/dollsmp-ffi` |

`HANDOFF.md` §9 rule 1 is unambiguous: **"No UE4SS, no Lua. Everything in-game is in
`dxgi.dll`."** `tools/coop-native.ps1` enforces it — it runs `build/remove-ue4ss.ps1`
(whenever an instance still has `dwmapi.dll` or `UE4SS.dll`) and *refuses to launch* if
either is still present, because "the old Lua co-op mod writes the same
`DollsMP\dmp_out.bin` the DLL writes and spawns its own puppet, so with both present there
are two writers on one file and two dolls for one peer."

### A.1 Process injection — the proxy-DLL loader

There is no `CreateRemoteThread`, no injector tool. The game itself loads the mod, because
the mod **is a DLL the loader resolves by name** and is placed next to
`DollsNest-Win64-Shipping.exe`:

```
Shipping today:         <Game>\Binaries\Win64\version.dll       (ours)
                        <Game>\Binaries\Win64\version_orig.dll  (the real System32 copy)
```

- `mod/native/src/exports.h` is **generated** by `tools/gen_proxy_def.py` — "Export names
  taken from `C:\Windows\System32\version.dll`" — and `proxy.cpp` forwards every one of
  those exports to the real DLL at runtime, **checking that each resolved pointer lands back
  inside System32**. A failed forwarder would otherwise "show up only as a loader failure in
  some unrelated module that imports this DLL later."
- **The proxy moved from `dxgi.dll` to `version.dll`, and the reason matters.** The
  launcher now *deletes* `dxgi.dll` and `dxgi_orig.dll` from the co-op folder and hijacks
  `version.dll` → `version_orig.dll` instead, because "an out-of-System32 `dxgi.dll` breaks
  the Steam overlay" (`crates/dollsmp-launcher/src/main.rs:630-650`). The early docs,
  `README.md` and `mod\native\build.bat` still say `dxgi.dll`. **For Queen's Domain, pick
  the proxy name from the game's actual import table and check it against Steam's overlay
  and any anti-cheat — do not copy the name.**
- Nothing is written to the 10 GB pak. The mod is loose files only. `tools/backup.ps1`
  exists because of this rule and deliberately does **not** back up the pak.

### A.2 Hooking — byte-verified RVAs, then MinHook

`mod/native/src/targets.h` is generated by `tools/gen_native_targets.py` **from the shipped
image**, and pins the image identity:

```c
#define DMP_IMAGE_SHA256 "82776A61B1F5CA9A89CBD73A8545A6193DB4802EE9A70F7487851CAEF4225360"
struct DmpTarget { const char* name; uint32_t rva; const char* role; uint8_t check; uint8_t expect[16]; };
```

29 targets, each with the first 16 bytes of the function. At load, a mismatch means "this is
a different build -- not a typo here", and the mod refuses rather than half-working.
`check = 0` is used for zero-initialised globals (`GUObjectArray`, `GMalloc`), which are
validated at runtime instead (`dmp_reflection.h`). Roles are `hook` / `call` / `watch` /
`data`.

Cross-build support was added later: `dmp_build.h` + generated `dmp_build13.h`
(`DMP_XRVA(legacy, X)`, `DMP_XEXP`, `DMP_B`) let one binary serve two game builds, with
`g_dmpBuild` set at startup from the game's code id. **1.3.0 was then dropped** ("Steam users
cannot stay on it"), which is itself a lesson about maintenance cost — see §C.10.

### A.3 The per-frame tick

Three successive mechanisms, all still present:

1. **Detours on `UGameplayStatics::GetPlayerPawn` and `GetWorldDeltaSeconds`** — a
   game-thread point at ~10 calls/s. `Detour_UGameplayStatics_GetWorldDeltaSeconds`
   (`proxy.cpp:1155`) drove everything for the first ~22 docs.
2. **Doc 23: `ProcessEvent` MinHook** (`DmpFastTickInstall`, `Detour_ProcessEvent_FastTick`,
   `proxy.cpp:5183/5306`) — runs `T9Tick` after any actor's `ReceiveTick`, ≥4 ms apart.
3. **Doc 24: the same hook, but keyed on the local pawn's own `ReceiveTick`** —
   `g_tickFromPawn = 1`. This fixed a real defect: *"sampling/drawing after 'any actor's
   tick' changes phase every frame → use the local pawn's tick"* (F-24-4). Measured
   `FAST TICK: 70–92 ticks/s`.

`T9Tick` (`proxy.cpp:1821`) is the single game-thread entry point and calls, in order:
death watcher, `CoopTick`, reflection resolve, `DmpObjProbe`, `DmpPuppetProbe`,
`DmpPuppetLoop`, `DmpPuppetDressRecheck`, `DmpCoopPublishLocal`, rescue, focus, F5, revive,
overlay.

### A.4 Threads

| Thread | Owns |
|---|---|
| game thread | **everything that touches engine objects** (`T9Tick`) |
| `CoopWriterThread` | **all file I/O** |

The split is not stylistic. F-8 is a resolved hang where "the game's main thread is blocked
inside `std::fs::rename`, reached from our own `DmpCoopPublishLocal`" — a frozen game. Since
then the rule is absolute: the game thread hands a record to the writer through a seqlock
(state) / SRW lock (blobs) and never opens a file.

### A.5 Reflection without UE4SS

Replacing UE4SS is the largest single piece of engineering in the tree and it is where the
reusable *techniques* live:

- **`dmp_uobject.h`** — the object array (`GUObjectArray`, stride **0x18 chosen by
  measurement**, round-trip 64/64, `NumElements = 259999`) and `UObject::ProcessEvent`
  resolved by measurement. "A stride read wrong returns plausible garbage rather than
  faulting, which is why it is measured, not assumed."
- **`dmp_objscan.h`** — bulk scans. One pass for many names, and **one `VirtualQuery` per
  64K *chunk*, not per object** ("a syscall per object is not slow, it is a game-thread
  freeze").
- **`dmp_ufunc.h`** — the ProcessEvent **parameter buffer**. The insight that makes it safe:
  *"A UFunction reads and writes its parameter buffer using ITS OWN compiled-in offsets.
  Those offsets are correct by construction."* Layout convention: **arguments first, return
  value last**, at natural alignment.
- **`dmp_reflection.h`** — resolves the named functions into `g_pupFn*` slots.

### A.6 The file bridge (game ↔ sidecar)

The game process has no socket. It writes/reads one file per lane in
`<Win64>\DollsMP\`; the sidecar does the networking.

**State record** — `dmp_out.bin` / `dmp_in.bin`, magic `DMPB`, version 3:

```
magic(4) "DMPB" + version(2) + seq(4) + stamp_ms(4) + body(145) + checksum(4) = 163 bytes
```

Body (from `crates/dollsmp-server/src/clientproto.rs`, `STATE_BODY_LEN = 145`, with offsets
pinned by `crates/dollsmp-sidecar/tests/wire_format.rs:84-142`): tick@0, form@4 (0 humanoid /
1 machine / 2 transitioning / **254 no pawn** / **255 peer gone**), position@5, rotation@17,
velocity@29 (3×f32 each), health@41, max_health@45, shield@49, energy@53, `heat`@57 (a
deliberately **sourceless reserved 4-byte lane** — there is no heat attribute in the game),
`b_is_dying`@61, ability fields, `target_entity`@72, 9× `{asset_id u32, level u8, color u8}`
legacy loadout@77, `loadout_revision`@131, `move_mode`@135, `custom_mode`@136,
`sample_ms`@137, `map_token`@141. A compile-time `const _: () = { assert!(...) }` pins the
sum to `STATE_BODY_LEN`.

The checksum is FNV-1a32. The version is bumped in **three places at once** — the Lua/native
`BRIDGE_VERSION`, `dollsmp_server::CLIENT_PROTOCOL_VERSION`, and the Rust `pack_record` — and
the Rust side asserts the body length so the two implementations cannot drift.

Implementation: `crates/dollsmp-ffi/src/bridge.rs` (`pack_record`, `unpack_record`,
`Session::publish/poll/peer_view`), linked into the DLL as a staticlib and exercised by a
**10-bit self-test** (`dmp_ffi_selftest`) that checks bitstream, quantizer, RNG, varint, the
163-byte round-trip, the `form` byte offset (18) and that a flipped byte is rejected.

### A.7 The lanes

Every lane is the same shape: a magic, a `u32` revision, a chunked payload. The sidecar
`BlobLane` (`crates/dollsmp-sidecar/src/main.rs:425`) watches the out-file, chunks with
`look::split`, sends `ClientMsg::Event { key, kind, data }`, reassembles with
`look::Reassembler::for_lane(magic, max_len)`.

| Lane | Files | Magic | Kind | Rate | Max |
|---|---|---|---|---|---|
| state | `dmp_out.bin` / `dmp_in.bin` | `DMPB` | (direct) | 60 Hz | 163 B |
| appearance | `dmp_look_out/in.bin` | `DMPL` | `0x4C` | on change + 2 s | — |
| world | `dmp_world_out/in.bin` | `DMPW` | `0x57` | on change + 2 s | 61,440 B |
| entities | `dmp_ent_out/in.bin` | `DMPE` | `0x45` | 20 Hz host / 10 Hz peer | 8,192 B |
| player FX | `dmp_pfx_out/in.bin` | `DMPP` | `0x50` | 10 Hz | 8,192 B |
| chat | `dmp_chat_out/in.bin` | `DMPC` | `0x43` | 25 Hz / keep 750 ms | 4,096 B |
| voice | `dmp_voice_ctl.bin` / `dmp_voice_st.bin` | — | `0x56` | 20 Hz | — |

Plus **`dmp_clock.bin`**, a free-running beacon: the game has *no usable clock* (see C.4), so
the sidecar hands one down (8-byte u64, rewritten every 100 ms). Also `dmp_role.txt`
("host"/"client", padded to equal length so a reader never sees a partial string),
`dmp_status.txt` (read by the HUD for the partner's name), `dmp_identity.bin` (16-byte
persistent install id — random, deliberately **not** hardware-derived, because "a
fingerprint collides for two players on one machine, follows a player to a new machine, and
leaks something about the host").

**Frame and chunk format** (`crates/dollsmp-sidecar/src/look.rs`): magic(4) + version(2) +
reserved(2) + `revision u32` (FNV-1a32 of the payload) + `payload_len u32` + payload +
checksum(4) = a 16-byte header; chunks are `revision u32, index u8, count u8` + ≤900 bytes
(`LOOK_CHUNK_MAX = 900`), i.e. 906-byte messages kept under the deliberate 1200-byte
"never fragmented" budget. `Reassembler::push` is order-independent, duplicate-tolerant and
re-validates the assembled frame. **That 900-byte choice is the reason no fragmentation was
ever needed — and it is also the ceiling on every bulk lane.**

### A.8 The sidecar

`crates/dollsmp-sidecar` — one process per game, owns the UDP socket.

- Reads `dmp_out.bin` (held handle, rewrites in place), sends `ClientMsg::State` to the relay.
- Receives peer state, writes `dmp_in.bin`.
- Forwards each blob lane both ways with chunking/reassembly, and re-sends the whole frame
  on change and on a timer, so a late joiner or a lost chunk heals.
- Poll loop sleeps **1 ms** (`timeBeginPeriod(1)` in sidecar, relay **and** the DLL's writer
  thread — "`sleep(1 ms)` is ~15.6 ms per process on Windows unless `timeBeginPeriod(1)` is
  called in *that* process", F-24-2).
- `voice.rs` does capture/Opus/3D panning; `dmp_talk.h` documents that the Opus decode path
  "must never run" in some configurations.

### A.9 The relay

`crates/dollsmp-server` — `relay.rs` (82 KB), `clientproto.rs` (96 KB), `lib.rs` (59 KB).

- **Session**: `Session` (`lib.rs`) with `MAX_PLAYERS = 2`; **the first player to join is the
  host** (`Session::host()`), and join order is the canonical authority.
- **Wire**: magic `DMPC`, 7-byte header (`magic(4) + version u16 + type u8`),
  `CLIENT_PROTOCOL_VERSION = 3`, `STATE_BODY_LEN = 145`. Fifteen message tags, `#[repr(u8)]`:
  `Hello=1, Welcome=2, State=3, Event=4, Ping=5, Pong=6, Bye=7, PeerUpdate=8, Resync=9,
  ClientReady=10, SessionStarted=11, StallBegin=12, StallEnd=13, Digest=14, Leave=15`.
  Unknown codes are a **hard error**, so "an old peer meeting a new control message fails
  loudly" rather than silently. It is "a router, not a protocol" — plain `send_to`, no seq,
  no ack. Reliability lives above (repeated state, idempotent events) and below (the core
  `DMP1` layer, which is built and tested but **not on the live path**).
- **Join barrier**: `can_start()` = 2 players and all ready; `start()` latches; `reopen_barrier()`
  clears readiness but never `started`, so a stale `ClientReady` cannot re-close it (this is
  the map-travel path). Both peers get `SessionStarted { world_seed, snapshot_revision }`.
- **One-shot events**: `Session::accept_event(key)` keeps a `BTreeSet<u64>`, rejects
  duplicates, and bounds history at 4096 by evicting the **smallest** key — which is only
  sound under a monotonic key contract, `(hostEpoch << 24) | hostSeq`, **never a hash**. The
  failure mode of a non-monotonic key is pinned by a test.
- **Liveness** (`liveness.rs`, all game-neutral): `HELLO_REFRESH_MS 1000`,
  `SESSION_STALE_MS 6000`, `READY_TIMEOUT_MS 45_000`, `REAP_MS 60_000`,
  `RECONNECT_GRACE_MS 120_000`, `SETTLE_MS 500` — asserted strictly increasing, because "the
  45 s ready-timeout must sit *inside* the 60 s reap". `StallClock` *suspends* deadlines over
  bracketed stalls (`LevelTransition`, `FormTransition`, `SaveLoad`, `SnapshotApply`) and
  never extends them.
- **Fault injection**: `NetImpair { delay_ms, jitter_ms, loss_per_10k }`,
  `parse("delay,jitter,loss")`, re-read every second from `run/net.txt`. This is why the mod
  can claim "20 % loss, 40 ms jitter → 67 cm mean error".

### A.10 Protocol layers — three nested formats

`docs/sync/12-protocol-requirements.md` §4.1 spells out the trap:

| Leg | Format | Crosses a lossy link? |
|---|---|---|
| game ↔ sidecar | `DMPB`, 163 B record in a file | no |
| sidecar ↔ relay | `DMPC`, 7 B header over UDP, no reliability | **yes** |
| peer ↔ peer | `DMP1`, 18 B header + bit-packed payload, ack/seq/RTT/delta | yes, **but not used live** |

The same document specifies the channel model the live code approximates: **R0 CONTROL**
(reliable/ordered/idempotent), **R1 STATE** (unreliable latest-wins, 30–60 Hz, coalesced one
datagram per tick), **R2 EVENT** (reliable per-author FIFO), **R3 WORLD** (reliable
unordered idempotent, at-most-once effect), **R4a ADVISORY**, **R4b COSMETIC**
(fire-and-forget), **R5 BULK** (chunked, resumable), **R6 LIVENESS**. Priority:
`R0 > R3 > R2 > R6 > R1 > R4a > R4b > R5`.

### A.12 World-sync model (the part the new game needs most)

From `HANDOFF.md` §1 doc 27 and `dmp_world.h`'s header:

> **State, not events** — the host repeats its whole world, a peer repeats its open
> requests, damage is a running total — a lost or duplicated datagram changes nothing.
>
> **The rule the owner set: every connected player's world follows the HOST's world. Never
> the other way round. A peer's own save never changes the host's world; what a peer DOES
> during the session … is a REQUEST the host applies to its own world, and the peer then
> receives it back like everybody else.**

The "world" is literally the game's own persistent save object: `UDAPersistentSaveGame` with
**eight containers** — EventParams (gates, walls, portals, elevators, quest counters),
ReachedDistricts, ReleasedCheckpoints, BossStates, NPCStates, ReadDialogues,
ReadDialogueChains, and a "dead until next rest" list — read raw and written with **the
game's own `Emplace`/`Add` instantiations called by address** (F-27-2: "no allocator of ours
touches engine memory").

The blob is sectioned (`dmp_world.h:314-363`); the ids are part of the wire contract:

| Section | Meaning |
|---|---|
| `0x10 + cat` (`CAT_BASE`) | the save containers, by category (event params, read marks, NPC states, chains, …) |
| `0x30` PLACE | level, NG+ cycle, boss mode |
| `0x31` TRAVEL | level travel |
| `0x32` DEAD | GUIDs of characters dead until the next rest |
| `0x33` DOORS | auto-doors this machine holds open |
| `0x34` PROPS | landmines/destructibles not as the level made them (the ledger) |
| `0x35` RTPROPS | runtime-spawned non-characters (areas, smoke, spheres) |
| `0x36` MOVERS | elevators/platforms/monorails currently moving |
| `0x37` RULES | the sender's `[Rules]` (the host's are the session's) |
| `0x38` RESET | world-reset count (rest, Returner) |
| `0x39` CHOICES | dialogue choices answered lately |
| `0x3A` BUILD | DLL build hash, game-build verdict, switch files |
| `0x3B` ARENA | units released in the sender's save |
| `0x3C` ACH | shared achievements |
| `0x3D` LEDGER | peer→host: what the peer did while the host was away |
| `0x3E` DLGLOCK | the NPC this player is talking to (+ seq) |
| `0x3F` PRESENCE | what the sender is *doing* (missing = normal WORLD) |

## B. Reuse matrix

Verdicts: **AS-IS** (copy, change nothing but the name) · **PORT WITH LIGHT EDITS** (paths,
constants, names) · **ADAPT** (keep the design, rebuild parts) · **REWRITE** (the design is
the only thing that survives) · **DROP**.

### B.1 Rust workspace (24,328 lines, ~470 tests)

| Component | Path | What it does | Verdict | Why |
|---|---|---|---|---|
| `dollsmp-core::bitstream` | `crates/dollsmp-core/src/bitstream.rs` | LSB-first bit writer/reader, varint, zig-zag, f32 | **AS-IS** | Zero deps, `#![forbid(unsafe_code)]`, deliberately matches UE's `FBitReader`/`FBitWriter` convention. 13 unit + 5 property tests pin the bit order. |
| `::quantize` | `quantize.rs` | `Quantizer`, `PositionBounds`, `RotatorCodec`, `VelocityCodec` | **PORT WITH LIGHT EDITS** | The code is fully parameterised and UE-correct (cm, `FRotator` ranges). Only the *defaults* are Dolls-Nest-shaped: ±200,000 cm box, 22 bits/axis, 10,000 cm/s, 16-bit rotator. A smaller indoor game can cut bits and gain bandwidth. `max_error()` correctly includes one f32 ULP, not just half a step. |
| `::reliability` | `reliability.rs` | 16-bit seq/ack-bits window, `AckTracker`, `SequenceBuffer`, `RttEstimator` (SRTO = `clamp(srtt+4·jitter, 100, 2000)`) | **AS-IS** | Pure arithmetic, no game or transport knowledge. Explicitly **no congestion control** — correct for a 2-player link, and that assumption must be re-affirmed for Queen's Domain. |
| `::delta` | `delta.rs` | per-entity field deltas against an acked baseline, `BaselineStore` | **ADAPT** | Correct and well tested, but hard-capped at **64 fields per entity** with an unconditional `u64` mask and `u64` values (`delta.rs:93-99,146-153`). `docs/sync/12` F-003 shows the cost consequence: one changed *bit* costs the same ≈17 B as one changed 64-bit word. A UE property set will exceed 64 fields, so the mask/value widths must become variable. |
| `::desync` | `desync.rs` | FNV-1a64 digests per tick, strike threshold, per-entity divergence | **PORT WITH LIGHT EDITS** | `hash_snapshot` is order-independent by construction (sorts per-entity hashes) — a genuinely good idea. Only typed against `delta::Snapshot`. |
| `::rng` | `rng.rs` | PCG-XSH-RR 64/32, Lemire bounded, `SeedMixer` | **AS-IS** | Published golden vector test (`seed 42/stream 54 → 0xA15C02B7 …`). Deterministic across platforms is exactly what shared-RNG co-op needs. |

### B.5 Defects to fix *before* reusing (found in this audit)

1. **`RpcPayload for bool` cannot be encoded through `RpcTable`.** `bool` writes one bit
   (`ecs/src/rpc.rs:86-93`) but `RpcTable::encode` writes a varint length then
   `write_bytes`, which rejects a non-byte-aligned position → `NotByteAligned`. No test
   pushes a `bool`.
2. **Retransmit entries can leak in `dollsmp-net`.** `Connection::tick` calls
   `acks.evict_stale(...)` (`net/lib.rs:269`) which removes aged entries from the tracker but
   **not** from `Connection.retransmit`, so the packet is neither resent nor abandoned and
   `pending_reliable()` never drops.
3. **`make_header` conflates two meanings of "ack"** (`net/lib.rs:155-159`): `have_ack()` is
   the *peer* having acked *us*, which says nothing about which inbound sequence to ack.
4. **`DesyncDetector::compare_tick` counts a strike per call, not per tick** — comparing the
   same tick twice double-counts.
5. **`Packet` fields are public and `encode` casts `payload.len() as u16`** without
   re-validating `MAX_PAYLOAD`, so a hand-built packet bypasses the header check.
6. **The delta wire cost is fixed-width** — a one-bit change costs ~17 B. If Queen's Domain
   has many boolean quest flags, model the whole flag bank as **one entity of 64×u64**, never
   sharded (this is the conclusion `docs/sync/12` §4.1.3 rule 6 and `09` F-018 both reached
   independently).
7. **Pre-existing failing tests** (documented, not regressions): 8 in `dollsmp-server` and
   `dollsmp-sidecar\tests\wire_format.rs` field-offset check (141 vs 145). Do not carry these
   into a fresh workspace as "known failures" — fix or delete.
8. **The relay's `session_token` is minted, put in `Welcome` and never verified again** —
   the `ClientMsg` header has no token field, so the credential is advisory. Fine for a
   friends-only LAN mod; a real authentication story if the session is ever exposed.
9. **The relay's build-id check compares a client to itself.** `handle_client_ready` compares
   `ClientReady.build_id` against that same client's `Hello` build rather than the host's
   (`relay.rs:742-753`), so it can only fire if one client changes build mid-session.
10. **Two `ResyncReason` codes are dead on the wire** (`JoinError::AlreadyStarted` is never
    produced; `HostNotInWorld` is never emitted), and `applied_rev` / `loadout_revision` are
    explicitly discarded. Harmless, but do not build a protocol on them.
11. **`dollsmp-sim` cannot demonstrate sender-clock interpolation** — it pins
    `sender_ms == recv_ms` (`sim/src/lib.rs:309-322`). The mod's claim about it rests on
    `smoothing.rs`'s own test, not on the simulator. Do not inherit the claim.

### B.6 How much is actually reusable?

By lines, of ~156,000 total (24.3k Rust, 74.2k native C++, 18.2k Lua, 39.5k tools):

| Bucket | Lines | Reuse |
|---|---|---|
| Rust transport/protocol/session | ~17k | ~85 % carries over (edits, not rewrites) |
| Rust game domain (`dollsmp-game`) | ~1.7k | ~15 % (smoothing only) |
| Native proxy | 74.2k | **~5 % code** (pure decision headers), ~70 % *design* |
| Lua client | 18.2k | 0 % code, 100 % lessons |
| Tools | 39.5k | ~60 % carries over |

**Honest headline: about 25–30 % of the *code* is reusable as code, but the reusable part
is almost exactly the part that is hard to get right twice** (transport, reliability,
session, smoothing, PE tooling, packaging). **Roughly 80 % of the *knowledge* is reusable**,
and that is the real deliverable of this repo.

## C. Lessons learned / pitfalls

Every item below is a documented failure with a stated cause. These are the most valuable
artefact in the repository; a new mod that ignores them will rediscover them at the same
cost.

### C.1 UE4SS / Lua (why the whole first generation was thrown away)

| Lesson | Evidence | Applies to Queen's Domain |
|---|---|---|
| **UE4SS Lua has no sockets at all.** `socket`, `socket.core`, `ljsocket`, `mime`, `ltn12`, `ssl` are absent; `io.popen` exists but "spawning a subprocess per packet at 30 Hz would be catastrophic for frame time." | `RUNTIME-CAPABILITIES.md`; `mod/src/dllmain.cpp` header | If you reach for UE4SS+Lua, plan the sidecar/FFI split from day one, or go native. |
| **`UE4SS.dll` exports zero unmangled `lua_*` symbols**, so a side DLL cannot reach the host's Lua state. | same | Rules out the "cheap" hybrid. |
| **`ForEachUObject` with a Lua callback per object took minutes** (525 s of CPU) on a 260k-object array — every `IsA` crosses the Lua↔C++ boundary. | same | Never iterate the object array from a script, and never per tick from anywhere. |
| **`FindAllOf("StaticMeshActor")` returns 60,046 objects and building that array crashed the game.** | `main.lua:33-36` | Use `FindFirstOf`, or scan natively with chunked `VirtualQuery`. |
| **`StaticFindObject` with a path crashes** on this build when the path is not loaded; it does not return nil. | `main.lua:29` | Never resolve by path at runtime in UE4.27 shipping. |
| **`LoopAsync` is unsafe** — every crash correlated with it; `ExecuteWithDelay` chains instead. | `main.lua:38-41` | Avoid UE4SS async entirely, or serialize. |
| **A missing property read returns a non-nil ghost with a NULL class pointer**, and touching it is an AV that `pcall` cannot catch (`UE4SS!push_nameproperty+0x2c1`, `mov rcx,[rax+70h]`). | `main.lua:61-95`, `dmp_game.h` header | **The entire reason the mod moved to offsets.** For Queen's Domain: read offsets from a generated dump, never by name. |
| **`IsClass()` on a ghost follows the class pointer and crashes; `IsValid()` does not.** "The gate is `valid()` alone — NEVER `valid(v) or class_ok(v)`." | `main.lua:81-91` | Same class of bug exists in any reflection layer. |
| **`SpawnActor` of a Blueprint class crashes unless it runs inside `ExecuteInGameThread`.** Measured: native/direct OK, Blueprint/direct CRASH, Blueprint/game-thread 9/9 OK. | `main.lua:5-23` | Any UE4.27 co-op mod that spawns actors must respect the game-thread rule. |
| **A game-thread call is queued**, so the actor does not exist when the caller looks — verify from a later tick, not immediately. | `main.lua:20-23` | Same trap in a native mod when you defer spawn. |
| **`os.clock()` is CPU time, not elapsed** — measured 20.781 s while 7.0 s of real time passed (~2.97×), so every duration was stretched ~3× until a real clock was borrowed. | `main.lua:383-400` | **A game with no clock needs one injected.** Queen's Domain may expose `FPlatformTime`; if not, do what DollsMP did. |
| **UE4SS has at least four distinct failure shapes**: an `MSVCP140!Mtx_lock` deadlock with no owner, two crash families, a Lua/trampoline hang, and a null deref in `RC::Input::Handler::process_event+f0` reading `0x18`. | `ue4ss-removal/PLAN.md` F-7/F-9 | The conclusion was "stop loading it", not "find the bug". **For Queen's Domain: start native.** |

### C.2 Hooking and reflection correctness

| Lesson | Evidence | Applies |
|---|---|---|
| **Byte-verify every RVA at load.** `targets.h` carries 16 expected bytes per target and an image SHA-256; a mismatch means a different build. | `targets.h` | Regenerate for Queen's Domain; never hardcode an address without its bytes. |
| **A stride read wrong returns plausible garbage rather than faulting** — the object-array stride was *chosen by measurement* between 0x14 (0/64) and 0x18 (64/64). | `ue4ss-removal/PLAN.md`; `dmp_uobject.h` | Measure, then pin with a round-trip test. |
| **Parameter buffer layout is "arguments first, return value last" at natural alignment** — measured: `BeginDeferredActorSpawnFromClass` world@0, class@8, transform@16 (align 16), coll@64, owner@72, ret@80. | `HANDOFF_claude1.md` §4 | Re-derive per game; do not remember. |
| **`ProcessEvent` dispatches only if the function belongs to the object's class chain — and a wrong-class call does not fault.** So "call returned success" is meaningless. | F-12.17 | Report which class owned the function, or `UNVERIFIED`. |
| **Liveness is not "a plausible header".** A freed block keeps `InternalIndex` and a class pointer; reused memory has *another* object's. Real liveness = **the object array's slot at that index points back at the object**. | F-31-1, `DmpObjHeaderGuarded` | Same rule in any UE4 title; GC reuse is the top crash source. |
| **The world-context object is whatever Blueprint asked last**, and it dies with its level while the title screen never replaces it → a virtual call through freed memory. Read it only through a liveness gate (`DmpWorldCtxLive`, 18 call sites). | F-32-2 | Every cached `UWorld*`/context pointer needs this. |
| **A fault under a MinHook trampoline that moves `rsp` cannot be unwound** — no crash handler, no `__try`, the process just ends, and the only record is `%LOCALAPPDATA%\CrashDumps`. | F-32-1 | Keep crash-dump analysis in the loop from day one. |
| **A reflectively-called native gets the CALLER's frame**, not a parameter block: the VM hands `UFunction::Func` the frame and the thunk evaluates arguments itself (`GNatives` at `game+0x4A69E40`). | F-35-1/2 | Needed if you must mirror C++ abilities. |
| **`SetGenericTeamId` on the character is an empty function**; the team lives on the controller. | F-31-3 | Any "make them friendly" plan must be checked against the actual implementation, not the name. |

### C.3 Threading and I/O

| Lesson | Evidence | Applies |
|---|---|---|
| **Never do file I/O on the game thread.** A single `std::fs::rename` blocked the main thread and froze the game; at 60 Hz it also provokes real-time AV scanners. | F-8 | Same, always. One writer thread, seqlock handoff. |
| **`sleep(1 ms)` is ~15.6 ms unless `timeBeginPeriod(1)` is called in that process.** Call it in every process (sidecar, relay, DLL writer). | F-24-2 | Directly reusable. |
| **Only plain data may cross a script-worker boundary.** Holding a UObject handle off the game thread kills both instances (`RtlLeaveCriticalSection`, "attempted to release a resource it did not own"). | `main.lua:5734-5789` | Applies to any mod with a worker thread. |
| **One game-thread callback in flight, not one per pass** — otherwise a stalled game thread accumulates a backlog that runs all at once. | `main.lua:5891-5910` | Good pattern for a native queue too. |

### C.4 Clock, interpolation and rate

| Lesson | Evidence | Applies |
|---|---|---|
| **Interpolation needs a sample on either side of the render time**, so the peer must be drawn *in the past*. Extrapolating from "now" turns every late packet into a visible correction. | `main.lua:159-165`, `dmp_motion.h` | Core to movement sync in any game. |
| **The buffer must be adaptive** — measured jitter, grown immediately, shrunk with a time constant (`BUFFER_SHRINK_TAU_S = 0.6`, capped at 120 ms/s). A fixed 15 ms/s release meant "a single 60 ms spike cost 6.5 seconds of needless latency — measured". | `main.lua:167-195` | Directly reusable for Queen's Domain's peer body. |
| **A playout clock nudged by rate (0.88–1.12) beats recomputing "now − buffer"**, which inherits every wobble. | `main.lua:202-230` | Same. |
| **Lead-and-chase overshoots every turn; snapshot interpolation does not.** | F-24-3 | Do not "simplify" to chase-the-newest. |
| **Whole-millisecond stamps cost 3 cm at 30 m/s** → sub-millisecond byte in the sample. | F-24-5 | Keep sub-ms timestamps. |
| **Sampling after "any actor's tick" changes phase every frame** → use the local pawn's own tick. | F-24-4 | Find the equivalent per-frame anchor in the new game. |
| **Never extrapolate past a bound** — freeze instead; "flying a mech through a wall is far worse than a brief pause." | `MAX_EXTRAPOLATION_MS = 200` | Same trade for a human body. |
| **A discontinuity is not jitter**: snap on form change/teleport/respawn rather than interpolating across it. | `TELEPORT_THRESHOLD_CM = 800` | Same. |
| **60 Hz costs <10 KB/s and halves the age of the newest sample** — bandwidth was not the constraint; latency was. | `main.lua:138-151` | Budget accordingly. |
| **The final, tidy implementation exists and is small**: `crates/dollsmp-game/src/smoothing.rs`, ~400 lines, no engine, and its constants are a good starting point for any game — `render_delay_ms 100`, `max_extrapolation_ms 250`, `buffer_capacity 32`, `teleport_threshold_cm 2000`, clock drift `100 ppm`, and an implied-speed guard at `100_000 cm/s` (lower it for a walking-speed game). | `smoothing.rs:80-91,180-365` | Lift this file almost verbatim. |

### C.5 Actor construction (the hardest single area)

| Lesson | Evidence | Applies |
|---|---|---|
| **Spawn deferred, write the recipe, then finish**: `BeginDeferredActorSpawnFromClass` → `SetAssembleData` + `CustomizeData` + `TriggerData` → `FinishSpawningActor`. | doc 22, proven live | Generic UE pattern for "spawn a configured pawn". |
| **Writing the recipe is not the rebuild.** `SetAssembleData` moved `AssembleData@0x12C8` from 0 → 7 class pointers and the doll still rendered as legs, because the render uses nine separate **module actors** at `0x1598` that the class's own mesh does not include. | F-12.20/F-12.21 | **The single most expensive lesson.** Before believing a state write works, count the objects it is supposed to produce. |
| **The game's own registration path exists** — every module declares `ReceiveMerge(ADAMachine* OwningMachine)`; supply the actors, let the engine attach/socket/bookkeep. | F-12.21 | Look for the game's own assembly entry point instead of hand-attaching. |
| **"Mobility module" and "humanoid module" are whole characters**, so spawning them as "parts" produced two bodies with two health bars. | F-22-3, HANDOFF §4 | Check the class hierarchy before treating something as a component. |
| **Module sockets live on different parent meshes**, so hand-attaching to one mesh cannot work. | F-22-4 | Same. |
| **A spawned actor is `Static` by default and will not move**; set component Mobility to Movable (2) first. | `main.lua:55-56` | UE4 general. |
| **A puppet with no controller fires along world +X**, because `Shot` reads `GetController → GetControlRotation` and a controllerless pawn gets (0,0,0). | F-25-1 | Fix by sending the shooter's spawn transform, or give the puppet an aim source. |
| **Disable the movement component's tick once**, or it re-derives velocity toward zero and the mode back out of whatever you set — "the kind of change that looks applied in the log and has no effect in game". | F-12.16 | Critical for any driven puppet. |
| **`SetMovementMode` needs BOTH arguments**; one-argument calls are silently rejected. | F-12.16 | Same. |
| **Write velocity to the root *and* the movement component** — "which one a given animation graph reads is a property of the game's blueprint". | F-12.16 | Same. |
| **Destroying a Blueprint actor tens of ms after `SpawnActor` returns is an AV** — the engine is still constructing it. | `main.lua:5843-5851` | Add a minimum lifetime before teardown. |
| **A peer-gone marker must not be a value real data can hold.** Testing position `(0,0,0)` destroyed puppets of peers in a map transition; form 255 was chosen because no real state uses it. | `main.lua:5832-5856` | Design sentinels as reserved enum values, never as data. |

### C.6 Save files

| Lesson | Evidence | Applies |
|---|---|---|

### C.7 Authority and desync

| Lesson | Evidence | Applies |
|---|---|---|
| **State, not events.** The host repeats its whole world; damage is a running total. "A lost or duplicated datagram changes nothing." | doc 27 | The single most important design decision, and it maps directly onto quest sync. |
| **One-way rule, enforced.** "Every connected player's world follows the HOST's world. Never the other way round." A peer's action is a *request* the host applies, then broadcasts. | doc 27, `DmpWsPeerPlan` / `DmpWsHostAccepts` | Queen's Domain quest state should obey exactly this. |
| **Per-player things must be identified as such.** Loot is per player by construction (each machine rolls in `Die`); `EventSH_fl002` was excluded as per-player; dialogue *choices* are shared and locked. | doc 32 §2, doc 76, doc 83 | Decide the per-player/shared split per system, explicitly, and write it down. |
| **At-most-once effect needs monotonic keys and idempotent payloads**, not a hash. | `20-*`, `11` F-017 | Relay `Event` semantics; reuse. |
| **An event value must never be lowered** ("event_never_lower") — the host refuses a peer's write that would regress progression. | doc 76/79 | Directly applicable to quest flags. |
| **A dead player must still get a boss reward and the boss must still be marked dead.** The game ends the fight as a LOSS on that machine (`EndBossMode(Lose)`), and only the volume's `HandleBossModeEnded(Win)` pays anything — to PC 0. The fix is to *hold back* the loss while the partner lives. | doc 58, `dmp_progress_engine.h` | Any boss/progression system needs the same "held player" concept. |
| **The game's own one-shot gates are the sync surface.** A gate/hatch/wall is "unlocked" when its key EXISTS in `EventParams`; waking it means calling its own `AlreadyUnlocked`/`Unlocked`. | F-27-3 | Find the equivalent "fact consumed" model in Queen's Domain. |
| **Quests are just save containers.** Eight `UDAPersistentSaveGame` containers carried the entire quest system, and the write used the game's own `TSet`/`TMap` `Emplace`/`Add` instantiations called by address. | F-27-1/2 | **This is the model for Queen's Domain quest sync**: mirror the save's containers, not the UI. |
| **Dialogue needs a lock, not just replication.** Both machines ran the same talk Blueprint, and a race decided the choice. Rule: one player per placed NPC, published as *state* with a sequence number so a lost blob costs a beat and never the session. | `dmp_dlglock.h` doc 76 | Directly transferable. |
| **A dialogue open at death leaves an invisible unanswered choice** and was the likely route to a fatal error; the talk is now ended with the game's own end-talk on death. | doc 71 | Edge case worth planning for. |

### C.8 Testing discipline (the meta-lessons)

These recur more than any technical finding, and they are the reason the project eventually
converged:

1. **"A check that cannot fail is not a check."** The bridge probe reported success because
   `dmp_out.bin` was 163 bytes — while the Lua was writing that same file. `publish=0` was
   the actual failure, hidden by another process's evidence.
2. **"A measurement that never ran is not a measurement."** A branch that "never fired" was
   read as "broken" three times; the correct reading was "we do not know what would produce
   the presence".
3. **"`called=yes` is not evidence the call ran."** A wrong-class `ProcessEvent` returns
   without faulting. Fix: read back the object that was supposed to change.
4. **Read back the object, not the return value.** The dress step cost several identical game
   runs; adding a module-pointer count ended it in one run. "It should have been the FIRST
   thing written."
5. **A screenshot is not self-describing.** F-12.25.
6. **Hangs look exactly like "the other player is invisible".** Check `Responding` on the
   process before diagnosing sync.
7. **Take a minidump while hung** (`cdb -p PID -c ".dump /ma path; qd"`) before stopping
   anything; the 3-second/0.7 MB minidump produced the finding while a 5 GB `/ma` capture was
   still running.
8. **Attribute a frame only when the faulting frame is NAMED** — "UE4SS appears somewhere on
   the stack" is not attribution.
9. **One switch per subsystem** (`DollsMP-world-*.on`), so one broken part does not block
   testing the rest. There are ~45 such flags.
10. **Refuse with a reason rather than act on doubtful input** — every engine-facing step
    logs what it did and reads back the result.
11. **Run the acceptance test per case, with opposite expectations.** A blanket "the level
    did not reload on a death" passes on the broken build, because the failure is the rarer
    party wipe.

### C.9 Boot-time hacks (worth knowing before you spend a day on it)

| Lesson | Evidence | Applies |
|---|---|---|
| **The honest fix is config, not code.** Boot was ~27 s, of which 3–23 s was three non-interactive logo maps (`Boot_P`). Repointing `GameDefaultMap`/`ServerDefaultMap`/`TransitionMap` at the menu map took the menu from **~26.9 s to ~7.0 s with the logos never rendered** — "config-only. No Lua, no game function calls, nothing that can crash." | `tools/README-instances.md`, `mod/lua/fastboot`, `tools/boot-skip.ps1` | Try the ini before writing a hook. Two-headless-instance rigs pay this on every run. |
| **Three plausible fixes did nothing** — the doc lists them explicitly rather than letting the next person retry. | same | Record your dead ends; this repo does, everywhere. |
| **The clever version worked and crashed.** Walking the sequence's `Finished_*` stubs from Lua cut boot to 8.7 s and "looked like a clean win. **It crashed the game.**" It survives only as a one-call `SetVisibility` fallback. | same | A faster boot is not worth an unstable process. |
| **A/B test a suspected crash with dump counting, and redeploy first.** `tools/test-crash-ab.ps1` exists because "an earlier run 'proved' a fix by testing a stale deployed copy of the crashing version, which is a wrong answer with no error message." | same | Directly reusable discipline. |

### C.10 Packaging and distribution

| Lesson | Evidence | Applies |
|---|---|---|
| **Build the package with the static CRT** (`+crt-static`) so it runs without the VC++ redistributable. | `build-coop-package.ps1`, `tools/rustenv/cargo.cmd` | Same. |

## D. What the existing mod has NOT solved

Be explicit: \`README.md\`'s "puppet rendering not finished" is obsolete, but several real gaps
remain, and some are exactly the systems Queen's Domain needs.

### D.1 Genuinely unfinished

1. **Real-input quest coverage is thin.** The rig-driven sweep covered 169 steps across 10
   NPCs with **0 save differences on 1.3.1**, but the *real-input* walk reached only
   **25 of the guide's 190 talks**. `docs/sync/88-questline-walk.md` found "no sync defect in
   anything reached", which is not the same as "the questline is synced".
2. **Placement and survival are not verified, only save equality.** NPCs move and die
   (Yoyo to the Broodchamber, Hati's crucifixion, Yodo killing Aja/Calrad/Vorg). "Equal saves
   are necessary but not proof" — doc 83 §5.
3. **Quest branches are untested.** Only "first answer" and "last answer" were run, with
   `activate` rather than the real `start` funnel; mutually exclusive routes mean 190 steps
   are not reachable in one save.
4. **C++ abilities with cost/cooldown gameplay effects are not mirrored.** On a boosted copy,
   **267 of ~269** `GA_DAAIBoostJump` starts were refused; filling energy, removing the
   cooldown GE and forcing the movement mode changed nothing (0 started). "The blocker is
   something else (next: read the copy's ASC tags at a refusal)." Visual cost unmeasured.
5. **Cutscene scrubbing has no leader** — "each scrubs towards the other, 6 scrubs of
   849–1726 ms in one intro even in the clean control." Partially fixed (one forward step per
   intro) but the ping-pong was still observed.
6. **An invisible boss when a player enters the arena while the host is away** — the host's
   mirrored intro is refused, its boss stays hidden, and the peer mirrors "hidden on the host".
   Seen 4 shots in 171 s in one run; cause not proven.
7. **No-fire after a late entry with both players in the arena** — 48 shots then presses with
   0 shots; cause unproven.
8. **Deterministic random attacks are not synced.** "Where a random attack lands is each
   machine's own roll" (doc 34 open list), even though the *area* is mirrored.
9. **Homing projectiles on a puppet's shot lack a target id on the watcher** (open since
   doc 25 §6, partially addressed by the enemy registry).
10. **Only 2 players, and only loopback/single-PC LAN was exercised for most of the project.**
    Steam P2P exists (doc 73, `crates/dollsmp-launcher/src/steam.rs`) but two-PC testing is
    repeatedly listed as "open / two-PC testing" in docs 56, 57, 74, 80.
11. **Several doc-79/80/82 behavioural cases are written but "were NOT run to a result"**
    (rig unstable). The unit-check counts (1,506 / 1,576 world checks) are not the same as
    a gameplay pass.
12. **`README.md` itself is stale** and would mislead anyone picking the repo up — the first
    thing to fix in a fork.

**Where the authoritative remaining-work lists live** (do not re-derive them): 
`docs/sync/64-remaining-sync-work-handoff.md` (the handoff of everything still unsynced),
`docs/sync/66-implementation-plan.md` (the step plan), `docs/sync/37-sync-gap-audit.md` and
`45-sync-gap-audit-2.md` (two audits of gaps), `docs/sync/79-*` (19 fixes, rig pass pending),
`docs/sync/88-questline-walk.md` (real-input quest coverage), and `docs/sync/72b-handoff.md`
("what is done and NOT yet synced for 1.3"). These are the documents to re-read before
promising a feature is complete.

**Status honesty note.** The project's own convention distinguishes *built*, *unit-checked*,
*rig-verified* and *owner-confirmed*, and much of the late work is only the first two. Doc 79
says "**built**, unit-checked (1,506 world checks, 0 failed). **Rig pass pending** (T5)"; doc
80 says "the behavioural cases are written but were **NOT run to a result** (rig unstable)";
doc 72b is titled "what is done and NOT yet synced for 1.3" (Combat Trials are not fought the
way boss fights are, and the follower's trial rules differ). Treat the code as a strong
reference implementation and the *verification claims* as tiered, not uniform.

### D.2 Structurally not solved (design limits, not bugs)

- **A peer's copy is not simulated.** It is driven; AI is shut down. That is the right
  choice for 2-player co-op but means anything that requires local simulation of the peer
  (e.g. accurate local hit prediction) is absent.
- **Loot is per-player by construction, not shared.** "A host kill the peer never saw alive
  gives the peer nothing (ghosted); shared loot not done."
- **The live wire has no reliability layer.** `DMPC` is a router; the reliable core (`DMP1`)
  is "built and unit-tested, **not on the live path**". Everything reliable is achieved by
  re-sending whole state, which works at 60 Hz on a LAN but is not a general transport.
- **No fragmentation on the live path**, and bulk transfers are capped at 61,440 B per frame
  with whole-frame resend.
- **No NAT traversal / no matchmaking** — the launcher expects an address or a Steam tunnel.
- **No anti-cheat / integrity story**; the mod is a DLL in the game process.
- **Maintenance surface is enormous**: 47 headers, ~45 switches, two game builds, 12+ Lua-era
  probe mods left in tree.

## E. Concrete porting plan

### E.1 Decide the transport question first (it changes everything downstream)

DollsMP's sidecar exists **only** because UE4SS's Lua had no socket. In a native proxy you
already own the process, and `crates/dollsmp-ffi/src/lib.rs` says the file bridge "can be
retired in favour of a socket in the DLL, which is where the protocol core was always meant
to end up".

For Queen's Domain there are two viable shapes:

- **A. Keep the sidecar** (lowest risk, proven): game ↔ files ↔ sidecar ↔ UDP ↔ relay.
  You inherit `dmp_ffi`'s bridge, the lane plumbing and the whole debugging model, at the
  cost of one extra process and file-based latency (measured sub-millisecond, and irrelevant
  against network jitter).
- **B. Socket in the DLL** (cleaner, less tested): link `dollsmp-net` + a real
  `WinsockTransport` into the proxy and drop the sidecar. The `Transport` trait already
  exists; a real implementation and fragmentation do not.

**Recommendation: A for the first milestone, B as a later refactor.** The first milestone
must prove *game* sync, not transport novelty, and every debugging tool in `tools/` assumes
the file bridge.

### E.2 Phase order

**Phase 0 — substrate (nothing game-specific yet).**
1. Copy `tools/builddiff/` (`peutil.py`, `native_tables.py`, `fncarry.py`, `fnindex.py`,
   `refldump.py`, `targets_verify.py`), `tools/re/`, `tools/typecheck/`, `tools/backup.ps1`.
   Re-point the game path at
   `G:\Freespace\Queens_Domain\QueensDomain\Binaries\Win64\QueensDomain-Win64-Shipping.exe`
   (79,468 KB, UE 4.27, Steamworks 1.63 present).
2. Generate the first `targets.h`: `UGameplayStatics::GetPlayerPawn`,
   `GetWorldDeltaSeconds`, `GetPlayerController`, `ApplyDamage`, `K2_SetActorLocation`,
   `Possess`, `UObject::ProcessEvent`, `GUObjectArray`, `GMalloc`, `FName::FName/ToString`,
   `StaticConstructObject_Internal`, `BeginDeferredActorSpawnFromClass`,
   `FinishSpawningActor`, `OpenLevel`. Byte-verify all of them.
3. Measure the object-array stride (the 0x14-vs-0x18 test) and pin it with a round-trip test.
4. Stand up a **log + crash-dump + read-back** habit before writing game logic. Every
   engine-facing step logs what it did and reads back the result.

**Phase 1 — lift the Rust layer wholesale.**
5. New workspace: `qd-core` (= `dollsmp-core`), `qd-ecs`, `qd-net`, `qd-server`,
   `qd-sidecar`, `qd-ffi`, `qd-sim`, `qd-cli`, `qd-launcher`, `qd-launcher-gui`.

   than ±200,000 cm; you can buy precision or bandwidth).

**Phase 2 — the peer body (the "can we see each other" milestone).**

12. Construct the peer body through the game's *own* assembly path, not by `SpawnActor` on a
    sub-component (F-12.20/21). Find the equivalent of `ReceiveMerge`.

**Phase 3 — world facts (quest progression, quest items, loot, dialogue).**
This is the heart of the Queen's Domain requirement, and it is **one pattern applied four
times**: *find the game's own persistent "facts" container, mirror it host→guest, and make
the guest's writes requests.*

13. Locate the save/persistence object(s) and enumerate their containers. Write a
    `dnsav.py`-style codec *with the root-path guard built in*.
14. Define the fact model: event params / flags (monotonic, never lowered), read marks,
    NPC states, quest stage counters, item boxes taken.
15. Implement `DmpWsPeerPlan` / `DmpWsHostAccepts` equivalents — the one-way rule.
16. Wire the game's own "wake" calls (`AlreadyUnlocked`, `Released`, …) so a synced fact
    actually opens the door / starts the scene on the guest.
17. **Quest items and loot**: decide per-item whether it is per-player (drops) or shared
    (quest items). DollsMP's answer: drops per player, rewards paid to whoever earned them,
    and a *reward queue* so a held player still gets paid.
18. **Dialogue**: implement the one-player-per-NPC **lock as published state** with a
    sequence number (`dmp_dlglock.h`), plus "first answer decides for both", plus subtitle/
    voice relay as a one-way cosmetic lane.
19. Reuse the **held-player / lose-hold** logic (`dmp_progress_engine.h`) for any boss gate.

**Phase 4 — enemies and authority.**
20. Host owns enemy AI; guest's copies are driven (position/aim/health/death) with AI shut
    down. Reuse the **entity id by level-authored GUID** idea where available, else a
    stable spawn-lineage id (F-29-1: every runtime character comes from two spawn nodes).
21. Reuse `dmp_director.h` (which player an enemy fights) — it is pure and directly
    applicable to any 2-player boss.
22. Reuse `dmp_world_stream.h`'s idea: **load what is around both players**, so the host can
    decide everything near either of them.

**Phase 5 — packaging and hardening.**
23. Port the launcher + GUI, the save guard, the build/session handshake, the ini with a

24. Port `tools/make-test-instance.ps1`, `launch-instances.ps1`, `seed-saves.ps1`,
    `test-all.ps1`, and `bot/dmpbot.py` (driver + snapshot/diff). Write new scenarios.
25. Port `steam_mock/` early — it lets you test the tunnel with no second account.
