# D1 — Does dialogue pause or time-dilate the game?

## Verdict

> **DOES NOT PAUSE, and does not time-dilate globally. Confidence HIGH (0.85).**
>
> During an NPC dialogue the world clock keeps running (`UWorld::DeltaTimeSeconds`
> untouched, `bIsPaused` untouched). What the game does instead is
> **(a) lock the player's input** and **(b) freeze *enemies* individually by writing their
> per-actor `CustomTimeDilation`** through a dedicated `TimeDilationManager`.
>
> **One named residual:** `FS_PlayerChar::SetUpForDialogue` / `PrepareForDialogue` are
> Blueprint functions in a package that *does* contain a `SetGamePaused` call node
> (§D1.4), so I cannot exclude a `SetGamePaused` node inside those two graphs. It is one
> bit to check at runtime (§D1.6) and it is the only thing standing between HIGH and
> CLOSED.

Design consequence, stated up front because it is what the sync design needs:
**there is no clock divergence to design around.** The two machines' `WorldTime` keeps
advancing identically. The thing that must be replicated is *not* a pause bit but (i) the
per-machine enemy `CustomTimeDilation` freeze and (ii) the fact that one player is
input-locked. Both are cheap.

## D1.4 Where "pause" actually is: a separate, dilation-based subsystem `[P]`+`[I]`

The game has a `TimeDilationManager` (`LD45/Blueprints/TimeDilationManager`,
`LD45/Blueprints/TimeDilationManagement`, and a `TimeDilationModifierType` enum) whose
vocabulary is unmistakable:

```
IsPausedTimeDilationEnabled      (3 pkgs: TimeDilationManager, TimeDilationManagement, Base_LD45_GM)
SetPauseTimeDilation             (5 pkgs: EnemyBase, Base_LD45_GM, TimeDilationManagement,
                                        TimeDilationManager, FS_PlayerChar)
SetPausedEnemyTimeDilation       (8 pkgs: WeaponUpgradeMachine, Grimoire_Logic, Base_LD45_GM,
                                        TimeDilationManagement, TimeDilationManager, Checkpoint,
                                        NPC_Base, FS_PlayerChar)
IsTimeDilationPaused             (4 pkgs: FS_GameInstance, TimeDilationManagement,
                                        FS_PlayerChar, ItemMergeAnim_Comp)
IsEnemyPauseTDLEnabled           (3 pkgs: EnemyBase, Base_LD45_GM, TimeDilationManager)
```

and the enemy side is a subscription:

```
Enemies/EnemyBase:  Bind To Enemy Pause TDL
                    EnemySetPausedTDL__DelegateSignature
                    K2Node_CustomEvent_Paused
                    IsEnemyPauseTDLEnabled
                    Recalculate Local Time Dilation
                    CustomTimeDilation, bIgnoreTimeDilation, ParalysisShouldAffectTimeDilation
                    SetPauseTimeDilation, SetActorTickEnabled
```

`[P]` for the presence of that machinery in exactly those packages.

`[I]`, 0.65 — the reading: this exists because **`CustomTimeDilation` only does anything
while the world is running.** Under a real `UWorld` pause, `DeltaSeconds` is 0 and the actor
does not tick at all, so writing `CustomTimeDilation` there would be dead code. A whole
subsystem whose job is "recalculate the *local* time dilation of an enemy from a global
'paused' flag" therefore only makes sense if **the world keeps ticking** and enemies are
frozen individually. And it is `NPC_Base` — the dialogue-starting class — that calls
`SetPausedEnemyTimeDilation` and `DisableAllPlayerInput`/`EnableAllPlayerInput`, with no
`SetGamePaused` anywhere in it. `[P]` for the names; `[I]` for the mechanism.

So the picture during an NPC conversation is:

```
world ticks normally            (no UWorld pause; both machines' clocks agree)
  player input disabled         DisableAllPlayerInput / EnableAllPlayerInput   [P presence]
  enemies frozen individually   TimeDilationManager -> EnemyBase.CustomTimeDilation  [I]
  UI animates                   UMG lives on Slate, which ticks while paused anyway
```

## D1.6 How to close it in one probe (for the LIVE pass)

Cheapest possible — three calls, no hook required. From the mod's per-frame game-thread
tick (`FEngineLoop::Tick` = `0x007753A0`):

```
UWorld* W = *(UWorld**)0x04BA86B0;              // GWorld (09-live-substrate.md §6)
bool paused = ((bool(*)(UWorld*))0x029A43C0)(W); // UWorld::IsPaused  [P]
float delta = *(float*)((char*)W + 0x5B0);       // UWorld::DeltaTimeSeconds
float gtd   = ((float(*)(UObject*))0x028DF810)(W);  // GetGlobalTimeDilation, needs a BP-free path
```

Log those four values once per second while an NPC dialogue is open. `paused==false` and
`delta` still advancing ⇒ **D1 CLOSED as DOES NOT PAUSE**.
Belt-and-braces: also hook `APlayerController` vtable `+0xA88` (`0x028F3180`'s own call
site, `[P]`) and log every hit with its return address — that catches Falsifier 5 too.

Caveat on `UWorld::IsPaused` `0x029A43C0` `[P]`: its body consults a **byte at
`UWorld+0x620`**, `AWorldSettings+0x370`, and a float compare between `UWorld+0x5B4` and
`UWorld+0x5A0`. Do **not** read `+0x620` alone as "the pause flag" — call the function.

# D3 — Is there a dialogue / one-speaker lock already?

## Verdict

> **PARTIAL. There *is* a local dialogue lock, and it is three cooperating guards, not one
> flag. There is *no* cross-machine lock, and no concept of a second participant anywhere in
> the binary or the content — because the game is single-player. Confidence HIGH (0.85) on
> the parts, HIGH (0.95) on the absence of any cross-machine mechanism.**

So DollsMP's job here is smaller than it was there: the *local* exclusivity machinery
already exists and should be **driven**, not reinvented. What the mod must add is only the
arbitration between two machines.

*player* owns the global state and the UI. That division is the thing to preserve.

## D3.3 What is genuinely missing `[P]`

* No cross-machine arbitration. The game has no session, no peer, no RPC and no replicated
  state (ANALYSIS.md §1.4 / executive summary: *"Engine networking classes and
  `OnlineSubsystem*` plugins are compiled in, but no game class implements sessions or
  RPCs"*). Every guard above is **per-machine local state**, evaluated against a local NPC
  actor instance.
* Therefore, with two players:
  * `PlayerIsTalkingTo` on machine A's NPC instance says nothing to machine B;
  * `BlockInteract` on A's NPC does not block B's copy of the same NPC;
  * `RunningDialogue` on A's player says nothing about B's player;
  * and two *different* NPCs can be talked to simultaneously (which is arguably fine, but
    breaks anything the dialogue sets as world state).

## D3.4 What the mod should do

1. **Do not invent a lock.** Reuse `RunningDialogue` (player) + `PlayerIsTalkingTo` /
   `BlockInteract` / `ReenableInteract` (NPC) as the *local* expression of the lock, and add
   a replicated `{npcGuid, playerSlot, seq}` record on top. This keeps the game's own HUD,
   camera and input behaviour intact — inventing a parallel flag will desynchronise them.
2. **Replicate the lock as state with a sequence number** (DollsMP's proven shape, 06-sync-
   design §4.5): a lost packet costs a beat, never the session.
3. **First answer decides for both**, and the chosen branch id replicates — this is where
   `EFS_DialogueConditionType` / `EvaluateConditionSet` (`0x00EAE0B0`) matter: conditions
   must be evaluated against the *shared* `NamedSaveData`, not local flags, or the two
   machines offer different options (06-sync-design §4.5, analysis risk table).
4. **Mirror the input gate on the peer's authority model**: the talking player is input-
   locked locally already; the *other* player must stay free (do not gate them). This is
   the concrete reason D1's verdict matters — a real pause would have forced a global hold.

## D7.3 The plan

### Step 1 — reach the HUD (fully specified)

```
UWorld*  W   = *(UWorld**)0x04BA86B0;                    // GWorld
APlayerController* PC = GetPlayerController(W, 0);       // 0x028E0340
AHUD*    hud = *(AHUD**)((char*)PC + 0x2B0);             // [P] from GetHUD 0x02E7E300
UClass*  cls = *(UClass**)((char*)hud + 0x10);           // UObject::Class (09 §2.2)
// verify: cls->Name == "FS_HUD_C", cls->SuperStruct == AFS_HUD_Base
//         (AFS_HUD_Base::StaticClass() = 0x00E57F80, cache 0x049898B8)
```

### Step 2 — add the widget: pick one of three, in this order

**(A) Canvas overlay — recommended first. Zero new assets, matches what the game does.**
Patch the game's HUD object's vtable entry for `AHUD::DrawHUD`, call the original, then draw
the partner panel with `AHUD::DrawText` `0x02DCE0E0` (+ `DrawRect` `0x02942160`,
`Project` `0x02958890` for a world-anchored marker).
*Remaining derivation:* which slot. `AHUD::DrawHUD` is the **only** `AHUD` virtual that
dispatches a Blueprint event, and `AHUD`'s only `BlueprintImplementableEvent` is
`ReceiveDrawHUD` (its pair-table value is the resolver stub `0x02DCB680` in table
`0x03FA3728`, which is exactly the signature of a BP event with no native body — §D1.1
pattern). So at runtime: walk `hud`'s vtable and take the slot whose target body contains
`call qword ptr [reg + 0x220]` (ProcessEvent, slot 68). That is a 4-line scan and it is
unique to `DrawHUD` on this class. **This is the one open item in D7.**

**(B) A second UMG widget — the pretty path, needs a cooked asset.**
`UWidgetBlueprintLibrary::Create` `0x02402C00` with our `UUserWidget` subclass, then
`UUserWidget::AddToViewport` `0x023F7BB0` (or `AddToPlayerScreen` `0x023F6C40`).
Blocked only by *cook pipeline*, not by RE: the mod would have to ship a `.uasset`. Given
`README`-level constraints, treat this as Phase 5 polish.

**(C) Hijack the creation callback — no new class, no new draw code.**
Detour `UWidgetBlueprintLibrary::Create` `0x02402C00`; when the requested `WidgetType` is
`FS_PlayerHUD_C`, remember the returned instance. Then *reuse the game's own HUD widgets*
(e.g. `HUD_QueuedText_C` from `Player/Assets/Input/HUD_QueuedText`) as a text carrier for
partner state. Cheapest to build, ugliest to maintain.

### Step 3 — what to put in it (from the sync design)

Partner name, distance, HP bar (already a `FS_PlayerHUD` idiom: `EnemyStatusZone`,
`MagicPoisonMeterHUD`), and a "partner is in dialogue" pip — which is the visual half of the
D3 lock. `ShouldHideHUD` (4 packages: `FS_PlayerChar`, `FS_HUD`, `ShouldHideHUD`,
`FS_PlayerHUD`) is the game's own hide switch; the partner HUD must honour it and
`HideHUD`/`UnhideHUD` on the same events, or it will float over cutscenes.

## D7.4 What I did **not** establish

* `AHUD::DrawHUD`'s vtable slot (Step 2A's remaining derivation; method given).
* `UEngine::GameViewport`'s offset. I tried to pin it from a `GEngine`-dereference histogram
  over 1,164 references; the top candidates (`+0xB08` 78×, `+0xAF8` 33×, `+0x780` 28×) were
  not separable, so I am **not** guessing. It is not needed for plan A/B/C above.
* `AFS_HUD_Base`'s **own** superclass. The `FS_HUD_C → AFS_HUD_Base` link is proven
  (§D7.1). What is *not* proven is that `AFS_HUD_Base` derives from `AHUD`, because the
  registration stub does not carry the parent as an argument — the four register arguments
  are `package-name wide string`, `class-name wide string`, `StaticClass` getter,
  `Z_Construct`, and the fifth candidate `0x007746E0` is a `ret 0` placeholder, not a
  superclass getter. The evidence is indirect but consistent: `FS_HUD_C` implements
  `ReceiveDrawHUD`, and `A*_HUD_Base` only makes sense as an `AHUD`. `[I]`, 0.9.
  Confirmable at runtime in one line (walk `cls->SuperStruct` and compare with
  `AHUD::StaticClass()`).
