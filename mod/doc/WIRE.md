# QDCOOP wire format, version 1

Canonical specification. The Rust crate `qd-core` and the native proxy
(`native/src/qdwire.h`) must agree with this document byte-for-byte; the
golden vectors in `doc/vectors.txt` are generated by `qd-core`'s tests and
consumed by the native self-test, so a drift between the two implementations
fails a test instead of corrupting a session.

## 0. Conventions

- Little-endian throughout.
- `u8/u16/u32/u64/i32` are unsigned/signed integers of that width.
- `guid` is 16 raw bytes, **big-endian field order preserved from the game's
  `FGuid` memory layout** (`A:u32, B:u32, C:u32, D:u32` little-endian in
  memory, i.e. exactly the 16 bytes read out of `FS_EnemySaveState` keys).
  Both sides send the raw 16 bytes; no re-ordering, no string form.
- `str` is `u16 byte_len` followed by UTF-8 bytes. No NUL.
- No padding anywhere. Every field is packed.
- A datagram carries exactly one envelope. One envelope never spans two
  datagrams: oversized content is *split across ticks*, never fragmented
  (DollsMP 12 H-6: fragmenting an unreliable stream measured 92.4 % effective
  loss at 256 fragments).

## 1. Envelope

```
offset size field
0      4    magic      = 51 44 43 31   ('Q','D','C','1')
4      1    ver        = 1
5      1    kind
6      2    body_len            (<= 1200)
8      4    session              (0 until WELCOME assigns it)
12     4    seq                  (per-sender, monotonic, starts at 1)
--- 16 ---
16     n    body
```

`body_len <= 1200` enforces the datagram budget: 16 + 1200 = 1216 B of UDP
payload, inside the 1280 B IPv6 minimum MTU after headers, and inside
DollsMP's measured safe envelope. A sender that would exceed it splits across
ticks.

`seq` is used by the receiver only for (a) duplicate suppression on reliable
kinds and (b) the ack window. State kinds ignore gaps: absolute state that
arrives late is still correct.

## 2. Kinds

| kind | name | direction | reliability | rate |
|---|---|---|---|---|
| `0x01` | `HELLO` | peer → relay → host | reliable | once, retried |
| `0x02` | `WELCOME` | host → peer | reliable | once, retried |
| `0x03` | `KEEPALIVE` | both | unreliable | 1 Hz idle |
| `0x04` | `ACK` | both | unreliable | piggybacked / 10 Hz |
| `0x10` | `PLAYER` | each → other | unreliable, latest wins | 30–60 Hz |

| `0x16` | `EFFECT` | each → other | reliable | event (projectile spawned / ended) |
| `0x17` | `EFFECT_MOVE` | each → other | unreliable, latest wins | ~15 Hz per live projectile |
| `0x18` | `STATUS` | each → other | unreliable, latest wins | on change + 1 Hz |
| `0x19` | `ENEMY_DETAIL` | both | reliable | on change |

| `0x22` | `LEVEL_UNION` | both | unreliable, latest wins | 2 Hz + on change |
| `0x23` | `TRAVEL` | both | reliable | on change + 0.5 Hz |

| `0x27` | `LOOT` | both | unreliable, latest wins | on change + 1 Hz |
| `0x28` | `SUSPEND` | both | reliable | event |
| `0x29` | `BOSS` | both | reliable | on change |
| `0x2A` | `OBJECTS` | host → peer | reliable | on change + 5 s repair |
| `0x2B` | `ENEMY_SPAWN` | owner → follower | reliable | once per key |
| `0x48` | `PLATFORM_RIDE` | each → other | unreliable, latest wins | on change + 1 Hz |
| `0x50` | `DIALOGUE_VIEW` | each → other | unreliable, latest wins | on change + 1 Hz |
| `0x54` | `RESPAWN_DOWN` | each → other | reliable | event (a death) |
| `0x55` | `RESPAWN_UP` | each → other | reliable | event (a respawn) |
| `0x56` | `RESPAWN_REST` | each → other | reliable | event (a rest) |
| `0x40` | `KILL_XP` | each → other | reliable | once per death |
| `0x41` | `SAVE` | each → other | reliable | once per save |
| `0x30` | `LOG` | both | unreliable | event |

The design rule being followed (DollsMP 12 §4.6 E8): **the event channel is a
fast path; the state channel is the authority and the repair.** Every
`WORLD_FLAGS`/`ACTOR_STATES`/`INVENTORY` body is therefore the *complete*
current set, not a delta. A peer that missed a thousand messages converges on
the next one. Bodies are small enough that this costs nothing: the measured
progression payload is 11 keys, and the enumerated universe is 58 `cha_*` keys
plus stat fields.

## 3. Bodies

### 3.1 `HELLO` (0x01)

```
u8   proto            = 1
u32  build_hash       image SHA-256 first 4 bytes, little-endian
u8   role_wanted      0 = any, 1 = host, 2 = peer
str  save_level       the `SaveLevel`/`SavedArea` the sender is in
u16  display_name_len
bytes display_name
```

`build_hash` mismatch is a refusal, not a warning: the substrate is
byte-verified, so two different images have different RVAs.

### 3.2 `WELCOME` (0x02)

```
u8   role_assigned    1 = host, 2 = peer
u32  session
u32  host_tick        host's frame counter at accept
str  save_level       the level co-op may start in
u32  flags_rev        current revision of the host's flag bank
```

### 3.3 `KEEPALIVE` (0x03) — empty body.

### 3.4 `ACK` (0x04)

```
u32  seq              the seq being acknowledged
```

### 3.5 `PLAYER` (0x10)

```
u8   slot             0 = host, 1 = peer
u32  sample_ms        sender's monotonic ms at sample time
i32  x, y, z          position, units of 1/8 cm (so 268 m of range at i32)
i16  yaw, pitch       units of 1/65536 turn
i16  vx, vy, vz       velocity, units of 1/8 cm/s, saturated to i16
u8   move_mode        the game's EMovementMode (1 walking, 3 falling, ...), 0 = none
u8   action           bits 0-4 kind, bits 5-7 a counter bumped on every new move (so the
                      same kind twice still restarts on the receiver). Kinds: 0 idle,
                      1 attack, 2 hurt, 3 dying, 4 dead, 5 slash right, 6 slash left,
                      7 slash down, 8 thrust, 9 charge (held), 10 throw, 11 use item,
                      12 weapon swap, 13 cast, 14 charge-thrust (held before a stab),
                      15 shoot (gun/crossbow/launcher), 16 spin (scythe/flail),
                      17 flurry (claw/katar/cestus)
u8   flags            bit0 grounded, bit1 aiming, bit2 sprinting, bit3 crouched,
                      bit4 dialogue, bit5 menu
```

Size: 1+4+12+4+6+1+1+1 = 30 B.

`action` is sampled from the first-person arms' active montage
(`avatar::ClassifyMontage`; measured: every melee click plays
`Player_FPArms_Std_Charge_Attack_Montage` -> kind 1, the strike lands 0.33-0.58 s in;
the `Player_Slash_*` follow-throughs and the left hand's `MeleeResponse` are not new
moves). The classifier reads the WEAPON out of the montage name — the game names every
weapon's montages after that weapon — and picks the move that weapon makes, so a
hammer's alt is an overhead (7), a lance's is a thrust (8), a claw's is a flurry (17),
a scythe's a sweep (16) and a gun's a shot (15). The held item's mesh path is the
fallback when the name says nothing. The kind is 5 bits, so the three newer kinds needed
no format change. `flags` bit0 (grounded) is `MovementMode != MOVE_Falling`; the receiver uses it
for the airborne pose instead of guessing from vertical speed. Unreliable rows can
arrive out of order: the receiver takes `action`/`flags` only from a row whose
`sample_ms` is not older than the last one it took.

Position range: an `i32` at 1/8 cm spans ±2.68e8 cm, i.e. **~2 680 km**.  (An earlier
draft of this document said "268 m"; it was wrong by four orders of magnitude.  The
clamp is ±2 147 483 000 units, chosen so the value survives a `float` round-trip on the
C++ side without the undefined behaviour that a `float -> int32` conversion at 2^31
would have.)

### 3.6 `WORLD_FLAGS` (0x11)

```
u32  rev              sender's revision, minted by the host only
u16  n                total entries in the container on the sender
n × { str name, i32 value }
```

`rev` is the monotonic counter described in `qdflags.h`: a peer refuses to lower a
value, and a host increments `rev` on every write it originates. It is host-minted and
never minted by a peer (`E1b`: never let two peers mint keys in one space).

**Chunking — the decision this document previously left implicit.**  There is
deliberately **no cursor or "produced" field**.  `n` is the size of the sender's
container; the receiver learns how many entries arrived by parsing until the body ends.
A sender that cannot fit everything advances a local cursor and continues on the next
tick, and wraps when it reaches the end. An extra count field was tried and removed: it
has to be patched after the header is written, and a patched count can disagree with
the bytes next to it. Convergence does not depend on chunking at all — the container is
re-sent on change and at 1 Hz, so a lost chunk is repaired by the next pass.

### 3.7 `ACTOR_STATES` (0x12)

```
u32  rev
u16  n
n × { guid guid, i32 value }
```

Same no-cursor rule as 3.6.

### 3.8 `INVENTORY` (0x13)

```
u32  rev
u16  n
n × { str item_path, i32 count }
```

`item_path` is the soft object path the save stores, e.g.
`/Game/Items/KeyItems/AquaDoorKey_2.AquaDoorKey_2`. Paths are sent as text and
never as pointers (DollsMP lesson: "transmit appearance as class names / asset
paths, never pointers").

### 3.9 `ENEMY` (0x14)

```
u16  n                total rows this sender will send for this tick's batch
n × { guid guid, i32 x, i32 y, i32 z, i16 yaw, u16 hp, u8 flags }
```
`flags` bit0 alive, bit1 driven (the receiver must freeze its copy because the sender
runs this enemy), bit2 has-body, bit3 peer-owns (the sender has handed this enemy to
the receiver and freezes its own copy), **bits 4–5 the identity source** (below).

**Direction.** `ENEMY` is bidirectional even though the name suggests otherwise: the
machine that *owns* an enemy publishes its rows. Ownership follows the nearer player,
because the game's enemy AI only ever targets the local player (`GetPlayerCharacter`);
an enemy can only attack the partner if the partner's own machine runs it. A machine
that does not own an enemy freezes its copy (no AI, no tick, movement mode none) and
follows the owner's rows, exactly as the peer used to follow the host's.

**Identity.** `guid` is the enemy's key, and the pair *(source, guid)* is its identity:
two 128-bit hashes of different things can collide, so the source bits are part of the
key rather than a hint. There are three sources, tried in this order:

| bits 4–5 | source | key |
|---|---|---|
| 0 | `SPAWNER` | the authored `FGuid` of the enemy's spawner (`EnemySpawner_C.GetSaveGUID()`), the same key `StoreEnemySaveState` persists by — one spawner owns one enemy |
| 1 | `PLACED` | FNV-1a 128 of the actor's cooked path `"<world>/<level>/<object name>"` |
| 2 | `SUMMON` | FNV-1a 128 of `"<summoner key hex>:<x>,<y>,<z>#<n>"` |

A spawner GUID wins wherever it exists **and no other live enemy already holds it**: one
spawner owns one managed enemy (`CurrentManagedEnemy`), so a second enemy naming the same
spawner is a spawned one, not the managed one, and must not overwrite its key.

`PLACED` covers an enemy authored into the cooked level with no spawner. Both machines run
the same cooked package, so that path is identical on both. Only a genuinely authored actor
qualifies: a runtime spawn's outer chain also reaches the world, but the engine gives it a
per-machine name number, and such an actor is never given the placed key.

`SUMMON` covers a runtime spawn. Its key uses the **spawn point**, not a counter, because
the incremental object scan discovers enemies in whatever order each machine's `GObjects`
happens to hold them: an ordinal assigned in scan order would differ between the two
machines for the same enemy, while a position is shared. `n` (starting at 0) separates
summons of one summoner that appear at the same point to 1/100 cm; those are identical in
class and position and therefore interchangeable, which is the only place an arbitrary
numbering is safe.

A row for a hash-derived key (`PLACED` or `SUMMON`) that this machine does not know is
matched against the local records that were themselves derived from a position. If exactly
one sits within 300 cm of it, it is the same enemy and the local record adopts the sender's
key and source — the sender ran the spawn, so its key is the truth. An ambiguous match (two
candidates in range) is refused and logged, never guessed. A `SPAWNER` key is exact, so a
mismatch there is a genuinely different enemy and is never absorbed.

`hp` is a **fraction of the sender's max HP**, 0..65535 (65535 = full, 0 = dead; a
living enemy is never sent as 0). Not an absolute value: both machines run the same
enemy data, but the max can differ per machine (equipment that multiplies enemy HP is
worn by one player), and an absolute value would draw a different health bar on each.

**Dead rows.** Besides the live set, the host re-sends its recent deaths (the
`StoreEnemySaveState(hp = 0)` it captured, at most 64) as rows with `flags = 0`, `hp = 0`
and a zero position, up to 4 per datagram. A peer that was not looking when the enemy
died (area not loaded, datagram lost) learns of the death this way. Because they are
re-sent continuously, a dead row goes stale like a live one (5 s): when the host rests
(`ClearAllEnemySaveStates`) it drops its kill log, the dead rows stop, and the peer
stops treating those enemies as dead.

Size per row: 16+12+2+2+1 = 33 B. 24 rows = 792 B + 2 header = 794 B, inside
the 1200 B body cap, so one datagram per tick at 20 Hz = 15.9 KB/s worst case.

**Row budget.** At most 20 rows per datagram at N=2 (DollsMP 12 §4.1.1's
formula), remaining rows round-robin to the next tick. Never split a row. Here `n`
is the number of rows actually in this body, not a container total — the enemy stream
has no container, it is a snapshot of the live set.

### 3.9a `ENEMY_DETAIL` (0x19)

```
guid guid            the enemy's key, same as a row (the pair (source, guid) is its identity)
u8   anim            see the table below; 0 = nothing playing
u8   seq             bumps on every new montage, so a repeat restarts on the receiver
u16  status          the same bits as `STATUS.mask`
u8   boss            the boss phase the owner observed, 0 = not a boss / no phase
str  path            montage asset path, "" when `anim` is 0
```

Anim kinds: 0 none, 1 attack, 2 hurt, 3 die, 4 roar, 5 cast, 6 move.

Why this is a body of its own and not more fields on the row: a row is a *sample*
(20 Hz, latest wins, losing one costs a sample) while this is an *event* — a montage
starts once, a status mask changes when a debuff lands and again when it expires. It
is sent reliably and only on change, by whichever machine owns that enemy.

The montage is identified by **asset path, not index**. Both machines load the same
cooked assets, but the order in which each discovers them is its own; an index would
select a different animation on each side, and the failure looks like "the enemy
attacks with the wrong move" rather than like a sync bug.

`seq` is per-enemy and wraps 255 → 1, so a receiver keys "already applied" on the pair
(`seq`, `path`), never on `seq` alone.

Status bits are mirrored onto the copy only where the property actually exists on the
enemy class; a bit whose property is missing is logged and dropped rather than
invented.

`boss` is the one per-boss value the shipped build exposes to a sync layer, and 0 means
"no phase observed". It is **observed, never fabricated**: `Phase`, `bBoss` and
`OnSubStateChanged` exist only in the executable's name block and in zero cooked
packages (only `Queen_BP` declares a `NewPhase` of its own), so there is no shared field
to drive. A receiver that sees 0 never touches a phase.

**Rate limiting.** This lane is cosmetic but bursts exactly when a fight is busiest, and
it shares the reliable table with `INTENT`, `TRAVEL` and `DAMAGE`. It is therefore ranked
before it is sent: each change is scored by its distance from the **receiver's** player
(the machine that draws the copy), and the lane is bounded to 10 bodies per rolling
second with a per-enemy minimum interval (100 ms for a critical event near the player,
up to 2 s for a cosmetic one far away, never for a cosmetic one beyond 150 m). Attack,
hurt, death, cast and roar are critical — they are what a player judges the fight by —
while locomotion is ambience. A refused change is kept pending and retried on the next
pump, so the lane degrades to "later", never to "never".

### 3.9b `BOSS` (0x29)

```
guid guid            the boss enemy's key; all zero when the body names no boss
u8   flags           bit0 bar on, bit1 bar off, bit2 arena exit,
                     bit3 ask, bit4 ack, bit5 nack (Session 20 negotiation)
u8   phase           the owner's observed phase, 0 = none
u16  hp              the boss's HP as the same 0..65535 fraction an `ENEMY` row carries;
                     a bar-off carries the last value read, 0 on a kill
```

The two per-boss facts that are a **local call on each machine**, and therefore have to be
driven rather than inferred:

- **Health bar.** `PlayerStatsAndUtils_C.ActivateBossHPBar(Enemy, Group, __WorldContext)`
  is a Blueprint function library call whose `__WorldContext` is the *caller's* world, so
  each machine raises it on its own player for its own copy. The sender says whether the
  bar should be up; the receiver calls its own `ActivateBossHPBar` / `DeactivateBossHPbar`.
- **Arena exit.** `EnemySpawner_C.PlayerTeleportedOutOfBossArena()` is a zero-argument
  spawner event overridden by 20 boss-spawner Blueprints. The *cause* is computed per
  machine, but the *fact* — "a player left the arena" — is one bool, so the sender says the
  fact and the receiver raises the event on its own spawner.

**Phases are not expressible** and are not faked: there is no shared phase field in any
cooked package, and writing a guessed value would run the wrong Blueprint branch on one
machine only. `phase` carries what the sender could observe, and 0 is the honest answer
when it could observe nothing.

Reliable, on change only: a boss bar that fails to appear because a datagram was lost is
the failure a player reports as "the boss fight is broken".

**The one bar is negotiated, because a bar the partner cannot show is not shared.** The
game has ONE boss HP bar and `ActivateBossHPBar` binds it to the actor it is given, so the
host is the single selector. Session 19 made it select the most-damaged live boss and
publish it; measured live, the two screens still showed different bosses because the host
selected `03FDBC21`, a key the peer held no copy of at all (it was outside the 25 m mirror
radius), while the peer's own `17181166` was a key the host held as a standing death. The
selection is therefore a round trip:

- `ASK` (host → peer) — "do you hold a live copy of this key?". No state changes.
- `ACK` (peer → host) — yes, and the receiver may keep its own bar raised for it.
- `NACK` (peer → host) — no; the host marks the key ineligible for 3 s, chooses the next
  candidate, and re-arms that key's `ENEMY_SPAWN` class description (the peer may gain a
  copy while the fight is running). A silence for 1.5 s is treated as a NACK.
- `BAR_ON` is only sent after an ACK. If nothing is showable on both machines, **no bar is
  raised on either** — the honest agreement, not a full bar on one screen and an empty one
  on the other.

Liveness is the owner's: the machine that RUNS the enemy (`enemyown::OwnerSet::Running`)
answers with its own dead flag / HP, and a follower takes the owner's `ENEMY` row verbatim.
An explicit `BAR_ON` from the owner retracts a stale local death on the follower, so a key
the owner is showing alive cannot stay dead on the other side. A candidate also needs a
READABLE HP: measured, a boss 71 m away whose encounter was not running was ACKed, bound,
and sampled `hp=0` forever while the dragon being fought was never selected. Both machines
log `boss: bar key=<8hex> hp=<0..65535|-1>` once a second while the bar is up (`-1` is
"HP unreadable", never 0), and the bar-off carries the last value: the live proof sampled
the same key and the same HP on both machines down to 0, 28 ms apart.

### 3.9c `ENEMY_SPAWN` (0x2B)

```
guid guid            the enemy's key, the same one an `ENEMY` row carries
u8   flags           bit0 = the receiver should hold this as a mirrored copy
i32  px              position, the same 1/8 cm quantization a row uses
i32  py
i32  pz
i16  yaw
u16  hp              HP as the same 0..65535 fraction an `ENEMY` row carries
str  path            the enemy ACTOR's class asset path, "<package>.<object>"
```

A spawner only spawns while *its own* machine's player is inside its activation range
(`PlayerIsInActivationRange`, which reads `GetPlayerCharacter` — player 0 of that machine),
so an enemy whose spawner activated on one machine **does not exist at all** on the other.
Measured in `780_SZ_Depths`: the Green Dragon (`Dragon_Green_BP_C`, key `17181166`) is a
live actor on the owner and the partner "holds no copy of this GUID". Every other enemy
lane — rows, detail, boss, damage — is addressed to a *copy*, so on the machine with no
actor there is nothing to follow, nothing to hit and nothing to kill.

The rows already say a key is alive and where it is. What a row cannot carry is **which
class to construct**, and it cannot be derived: a summon's key hashes its summoner and a
spawn point, and a placed key hashes a path, so neither names a package. The class
therefore rides the wire as an asset path, for the same reason `ENEMY_DETAIL.path` does —
both machines load the same cooked assets in their own order, so an index would select a
different class on each side.

Rules that keep this a repair rather than a second simulation:

- **Only the owner sends it**, and only while the key is alive. A dead key is the death
  ledger's job, not a reason to construct a corpse.
- **Reliable, on change, once per key.** A missing copy that never appears because a
  datagram was lost is a partner fighting an invisible boss.
- The copy is constructed through the engine's **deferred spawn** pair, with `Paused`,
  `bIsAIDisabled`, `AutoPossessPlayer` and `AutoPossessAI` cleared in the window before
  `FinishSpawning` — the same window B7's player body uses, and the only place those
  properties still decide anything.
- It carries the owner's key from its first frame, has **no `OwningSpawner`**, and is
  marked so that it never publishes rows, is never persisted by `StoreEnemySaveState`, and
  never takes ownership of its own AI.
- It is **destroyed** when the owner's row says dead, when that row stops (the owner left
  the area), or on a world change / session end.
- Receiver-side switch: `MirrorSpawn`. It constructs a full gameplay enemy Blueprint whose
  own `BeginPlay` runs, so it was OFF until a live session proved it; **Session 16 proved it**
  (`item1` 15/15, `boss` 25/25 in `780_SZ_Depths`) and the compiled default is now 1. It stays
  a switch so a broken mirror can be turned off without losing the rest of the enemy lane.

### 3.10 `INTENT` (0x20)

```
u8   kind             1 = set flag, 2 = grant item, 3 = consume item,
                      4 = dialogue answer, 5 = checkpoint touched,
                      6 = actor state set, 7 = enemy hit, 8 = enemy record,
                      9 = placed object state
u32  based_on_rev     the `rev` of the container the sender last saw
...  payload, by kind
```

Payloads:

```
kind 1 (set flag):        str name, i32 value, u8 mode (0 = additive, 1 = absolute)
kind 2 (grant item):      str item_path, i32 count
kind 3 (consume item):    str item_path, i32 count
kind 4 (dialogue answer): guid npc, u16 line_index, u16 option_index
kind 5 (checkpoint):      str save_point_path
kind 6 (actor state set): guid actor, i32 value
kind 7 (enemy hit):       guid spawner, i32 damage_frac
kind 8 (enemy record):    guid spawner, i32 respawn_centi, i32 hp_centi
kind 9 (object state):    guid key, u8 shape, u8 state
```

**Kind 2** — an item the peer obtained that the host does not have. `count` is the peer's
**cumulative own contribution** for that path, not a delta: the number of that item the
peer holds that the host did not give it. The host applies only the increase over the
highest value it has already applied for that path.

Cumulative rather than a delta, because the grant is additive on the receiving side: a
delta resent after a lost acknowledgement would add the item twice, while a cumulative
value is idempotent — a repeat applies nothing, a lower value is refused (a use travels
as kind 3), a higher value applies only the increment. This is deliberately a different
rule from kind 1's `based_on_rev` gate: for a monotone counter a replay *is* stale, but
for a cumulative grant a replay is exactly what recovers a lost body. `based_on_rev` is
carried for diagnostics on this kind and is not the acceptance test.

The peer measures its own contribution as `local − (what the host granted this peer)`,
never as `local − (the host's total)`: subtracting the host's total would make an item
both players picked up independently cancel to zero and lose one of the two gains.

**Kind 3** — an item the peer used. `count` is the peer's **cumulative use** for thatpath, not a delta. The host's ledger removes only the increase over the highest value it
has already removed (through `SaveFunctions_C.TryConsumingItemFromInventory`, read back
with the native counter), so a retransmit and a reorder are exactly-once. While a use is
outstanding, the peer's grant target is `host count − outstanding use`, which is what stops
the next host body from handing the consumed item back. `based_on_rev` is diagnostic only,
for the same reason as kind 2.

**Kind 7** — the peer's player hit a copy the host is driving. `damage_frac` is the HP
the copy lost, as a fraction of its max in 1/65535 units (it may exceed 65535 for an
overkill), so the host scales it by its own max and applies it through the enemy's own
damage entry, `TryApplyDamage` (the `FB_Damageable` interface message). It is **not**
`UGameplayStatics::ApplyDamage`: that function is real (`0x028D2190`), but `EnemyBase_C`
never imports it and it fires no enemy kill, so a peer hit applied that way is silently
lost. This is the one intent that carries a
delta, and deliberately: damage is an event, not a state. It stays within rule E2
because `INTENT` is reliable and de-duplicated by `seq` (a resent hit is applied once),
and because the host's next `ENEMY` row is the absolute truth the peer converges to.
`based_on_rev` is 0 (there is no enemy container revision).

**Kind 8** — the peer killed (or saved the partial HP of) an enemy that it was running
**itself** because the host had no live copy (players apart: a spawner only activates
for its own machine's player). The three scalars of
`StoreEnemySaveState(WorldContext, Key, RespawnTime, RemainingHP)` in 1/100; the host
applies the record to its save, so the enemy stays dead on the host too. A record for a
copy the host was driving is never sent — the host wrote it itself.

**Kind 9** — the peer opened/activated a placed world object the GUID-keyed lane cannot
carry (3.20). `key` is the placed-object key, `shape` the class family and `state` 0/1 —
the same three fields an `OBJECTS` row carries, so there is one encoding to keep in step.
`based_on_rev` is the `OBJECTS` revision the peer last applied, and `0` means "no baseline
yet" (Session 8 R73's rule), not stale. The host applies the state to its own copy and
publishes the echo; the peer's `object intent confirmed` line is that echo.

`based_on_rev` is the acceptance gate (DollsMP 12 §4.6 E4): the host applies an
intent only if `based_on_rev >= ` the revision of the last state it sent. That
makes double-pickup structurally impossible rather than unlikely.

### 3.11 `DIALOGUE` (0x21)

```
u32  seq              increments per state change; a lower seq is discarded
guid npc
u8   slot             which player holds the conversation, 0xFF = free
u16  line             dialogue cursor: sequence index
u16  entry            dialogue cursor: entry index
```

`seq` is what makes a lost blob cost a beat rather than the session: the lock
is published as *state* and the newer state always wins.

**Use (SYNC-DESIGN §2.7, no global lock).** Each player publishes **its own**
conversation: `slot` is the sender's slot while it is talking and `0xFF` when it is not,
on change and again at 1 Hz (a sender silent for 5 s is treated as free, so a crash
cannot leave an NPC blocked). `npc` is a stable 128-bit id of the placed NPC actor
(FNV-1a over its object / level / world names — the same cooked package on both
machines); `line` is `CurrentDialogueSequenceIndex`; `entry` is 0 (not read yet). The
receiver makes that NPC non-interactable for its own player with the game's
`BlockInteract` / `ReenableInteract`, so the two players cannot run the same talk
Blueprint, while both remain free to talk to *different* NPCs at once.

### 3.12 `LEVEL_UNION` (0x22)

```
u16  bits_len         bytes in the bitset
bytes bits            one bit per index into the sender's visible-sublevel list
```

Both sides send their own set; the union is computed locally and applied
through the level manager (`qdstream.h`). Bits are indexed by the sender's
own list order, so the body also carries a name list on the first send:

```
u8   has_names
if has_names { u16 n, n × str level_name }
```

A receiver keeps the last name list per slot and maps bits through it. This
keeps the steady-state body small while never requiring a shared index to be
negotiated.

**What the module sends.** Names are short level names (`100_GR`, from the streaming
level's `WorldAsset` package path), and the list is the levels **the local game itself
wants visible** — never the levels shown only because the partner needs them, or the two
lists would hold each other up and the union could never shrink. It always sends
`has_names = 1` with exactly those names and every bit set, on change and every 2 s
(~20 short names fit one datagram; a list that does not is truncated and logged).

### 3.13 `EQUIPMENT` (0x15)

What the sender is holding, so the receiver's copy of its body holds the same.
Absolute and complete: `n = 0` means empty hands.

```
u32  rev              increments when the held set changes
u8   n                ≤ 4
n × {
  u8   hand           0 = right, 1 = left
  u8   mesh_kind      1 = static mesh, 2 = skeletal mesh (shown in its reference pose)
  str  mesh_path      "<package>.<object>", e.g. /Game/Items/Weapons/RustedSword/RustySword.RustySword
  10 × i32 xform      the mesh relative to its weapon root:
                      location ×100 (1/100 cm), quaternion x,y,z,w ×1e6, scale ×1000
}
```

The sender finds held items as visible `StaticMeshComponent`s and `SkeletalMeshComponent`s of
`WeaponVisuals_C`-derived actors attached to its pawn (`ScanLocalEquip`). Every hand
item's visual is one of TWO unrelated Blueprint roots — `WeaponVisuals_C` for the
weapons and `Dagger_Visuals_Base_C` for every dagger / thrown / off-hand item, neither
deriving from the other — so the scan accepts both and, for the one-offs, the
`<Item>_Visuals` / `<Item>_InHandVisuals` name the game gives them (pickups and
inspect-only props excluded). The receiver loads the mesh by path
(`LoadAsset_Blocking`) and attaches it to the body's `Weapon_R` / `Weapon_L` bone.
Asset identity is a path, never a pointer.

### 3.14 `EFFECT` (0x16) / `EFFECT_MOVE` (0x17)

A thrown weapon or spell of the sender's -- the game's "magic" (Fireball,
MagicFireDagger, ...) is a projectile actor deriving from `Dagger_Projectile_Base_C`.
It is not the only shape: the player's guns, the crossbow bolt, the rocket, the
spear/hammer throws, the arc projectiles and the travelling ground waves derive
straight from `Actor` and share no ancestor with it (qdcombatvfx.h lists them), so a
projectile is recognized by `ProjectileMovement` OR by the class name the game gave it,
never by one class.
Spawn and end travel as `EFFECT` (reliable); position updates as `EFFECT_MOVE`
(unreliable, superseded by the next). Same body for both:

```
u8   kind             1 = projectile spawned, 2 = ended, 3 = moved, 4 = melee arc,
                      5 = one Niagara system at a point (impact / cast VFX)
u16  id               the sender's handle; spawn, moves and end share it
str  class            "<package>.<object>" of the actor class (kind 1) or of the
                      Niagara SYSTEM (kind 5), else ""
i32  x, y, z          1/8 cm
i16  pitch, yaw       1/65536 turn
i32  vx, vy, vz       1/8 cm/s (i32: projectiles outrun PLAYER's i16)
u16  life_ms          lifespan of the copy
```

The sender sees a projectile begin play (`ReceiveBeginPlay` through the ProcessEvent
hook), keeps it if its Owner/Instigator is the local pawn, and reads it one frame later
(a thrower may set the velocity after spawning). The receiver spawns the SAME class as
a visual only: collision off before the actor finishes spawning, actor tick off
after (the hit trace lives there), lifespan set. It cannot hit or damage anything in
the receiver's world. Because it cannot collide, it would fall through the floor
where the real one bounces and rolls (measured: Fireball rolls ~5 s), so moves snap it
to the sender's position and velocity, and the end puts it where the real one stopped.

**Enemy projectiles.** A projectile whose Owner/Instigator derives from
`FS_EnemyCharacterBase` and carries a `ProjectileMovement` is an enemy's shot, and it is
published **only by the machine that OWNS that enemy** (`ENEMY.flags` bit3 clear and a
live row from this sender). The partner's copy of the shooter is frozen, so it should
never fire; but a copy that fired anyway would send a second projectile and the partner
would show two. Gating on ownership makes "one shot, one visual" a property of the
ownership model rather than of the freeze, and a shot from an enemy that has no identity
yet is not sent at all, because the partner could not attribute it.

Damage lands exactly once, on the machine that owns the shooter: that machine's own
projectile collides and traces normally, while the copy the partner spawns has collision
and actor tick disabled, so it is a visual and nothing else. Nothing is applied twice and
nothing is applied by the wrong machine.

**kind 4, melee arc** (reliable). Every swing spawns the weapon's arc FX
(`/Game/VFX/Melee/MeleeArc_Default` or the weapon's override) as a Niagara component
attached to the first-person `Arms`, about 0.2 s in, coloured by Blueprint-set user
parameters. The sender watches `Arms.AttachChildren` while a move plays and reports each
new Niagara child once:

```
class      "<system>|<param>=<v>[,<v>,<v>,<v>]|..."   values x1000 as integers;
           four values = LinearColor, one = float. Measured on MeleeArc_Default:
           User.Color1, User.Color2, User.Lifetime, User.Power, User.Charge
id         the arc's relative pitch (quantized like pitch)
pitch      its relative roll (the swing direction)
yaw        its relative yaw
```

Positions and velocities are unused. The receiver spawns the same system on the body's
mesh (whose frame is the arms' frame: Y forward, X left) at eye height with that
relative rotation and sets each parameter (`SetVariableLinearColor` / `SetVariableFloat`).
UE 4.27 stores a type HANDLE in the parameter store, not the type, so the sender infers
the type from the name (`*Color*` = LinearColor, else float).

**kind 5, a Niagara system at a point** (reliable, `CombatVfx=1`). Two things the other
kinds cannot carry:

* **The IMPACT of a projectile.** The copy cannot collide, so the game's own hit
  reaction never runs on it and a thrown dagger used to stop in mid-air. At spawn the
  sender reads the impact system off the projectile's attached Niagara components
  (the name rule is `*_Impact`, `*_ImpactFX`, `*_ProjectileImpact`, `*_Explosion`,
  `*_GroundBlast`; never a trail/muzzle/charge system in the same folder), and at the
  end it sends that system at the point the real projectile stopped. `class` is the
  system's path; the receiver calls `SpawnSystemAtLocation` with `bAutoDestroy`, so the
  copy's lifetime is the system's own.
* **A cast / charge / muzzle effect that is a WORLD actor.** The grimoire's
  `GrimoireDoMagic`, a weapon's charge glow and a gun's muzzle flash are not children of
  `Arms`, so the arc lane cannot see them. The sender watches actors that begin play
  inside a 2.5 s window after its own action byte changes, keeps one only if its
  Owner/Instigator is the local pawn, it is not a projectile, and it owns a Niagara
  component, and sends that system's path — at most 3 per window.

Both are visual only: a system, no actor, no collision, no damage.

### 3.15 `STATUS` (0x18)

The sender's visible status effects, absolute, latest-wins.

```
u32  rev
u32  mask    bit 0 magic fire, 1 magic poison, 2 poison, 3 disease, 4 weaken,
             5 heavy, 6 binding, 7 berserk, 8 ironskin, 9 radiant fruit
-- optional vitals tail (a body that ends after `mask` carries none) --
u16  hp      the sender's own player HP, whole points, clamped to 65535
u16  hp_max  its GetMaxHP
u8   flags   bit 0 valid, bit 1 dead (IsDead or hp <= 0)
```

The vitals tail is sent on change and with the 1 s refresh; the receiver draws the
partner's bar on its own HUD (`PARTNER  hp / max`, or `PARTNER  DOWN`) right after the
engine's `AHUD.ReceiveDrawHUD` dispatch, with the HUD's own `DrawRect`/`DrawText`. There
is no stamina field: this build's player has no stamina (the player Blueprint declares
none; `PlayerBalance` keeps only a leftover `BaseJumpStaminaCost`).

Read from the player's own components: `StatusEffectComponent_C.Applied` (by component
name: `PoisonStatusEffect`, `DiseaseStatusEffect`, ...),
`MagicFireEffectLogic_C.CurrentMagicFireDamagePool > 0`, `MagicPoisonDebuffLogic_C.Active`.
On the player these effects are screen overlays only; the receiver shows world FX on
the body. The game's enemy effects (`EnemyBase_C`: `Fire_CharFX`, `Poison_CharFX`,
`DiseaseCharFX`, ...) sample a skeletal mesh and the body is a poseable mesh, so they
draw only at the feet (measured; a master-pose skeletal copy did not help). They are
kept for the ground glow, and a mesh-free system is attached at four bones: the blue
brazier flame for magic fire, the poison fishman projectile FX for poison (wisps) and
magic poison (magenta). Disease, weaken, heavy and binding have no stationary
mesh-free look in the game's content; the buffs (7-9) have no world visual in the game.

### 3.15a `TRAVEL` (0x23)

```
u32  seq             bumps on every change
u8   role            1 = host, 2 = peer
u8   phase           0 = in-world, 1 = hard begin, 2 = arrived, 3 = resume, 4 = area
str  map             short map name, e.g. `100_GR`
str  dest            the destination the sender just took, "" when not travelling
```

The world is announced rather than inferred. The session normally lives inside one
persistent level plus streamed sublevels, but hard transitions exist (the cutscene
maps, `900_SipehaWorld`, `990_B33sment`), and after one the two machines are in
different worlds where every absolute body means something different.

Both machines send this (on change and every 2 s). A receiver that disagrees does not
act: it logs the divergence once and stops applying the partner's `LEVEL_UNION` names,
enemy rows, enemy detail and dialogue until the names match again. The mismatch is
debounced, because a transition produces a second or two of disagreement while levels
finish loading.

`dest` is what makes the announcement actionable. It names the placed actor carrying the
game's own `LocationData` (a teleporter, a checkpoint, a cutscene trigger) as
`<actor>/<world>`. Both machines run the same cooked world, so the same actor exists on
both: the receiver resolves it by name and drives its own travel entry point, rather than
the sender teleporting somebody else's pawn. Empty when the sender is not travelling.

The measured entry point is `FS_PlayerChar.TeleportToLocation(LocationData, GreenFX)`,
with `EnemySpawner_C.PlayerTeleported()` as the world notification. `OpenLevel` is **not**
the in-world travel path: only menus, death and cheats import it.

**Hard transitions are a handshake, not a teleport.** A hard switch to a different
`UWorld` (`900_SipehaWorld`, `990_B33sment`, the `997/998/999_*` cutscene maps) cannot be
followed with `TeleportToLocation`: the destination actor does not exist in the
follower's world. The game's own entry for that is the native
`UFS_GameInstanceBase.LoadMapWithLoadingScreen(MapPackage)` UFunction (RVA `0x00E58F70`,
registration table `0x03950090`; it sets `bLoadingMap`, records
`CurrentlyLoadingMapPackage`, and starts an async world load). The mod calls it on the
follower when the sender's `phase` is `HARD_BEGIN`; `dest` is then the destination map
package path (`/Game/RuinsLevel/Maps/900_SipehaWorld.900_SipehaWorld`).

The `phase` field is what makes the handshake explicit:

- `0 NONE` — the ordinary in-world announcement, and the 0.5 Hz heartbeat.
- `1 HARD_BEGIN` — one machine has just crossed a world boundary. The other loads the
  same map. A machine that cannot load it refuses once, logs, and never retries that
  map; the session survives.
- `2 ARRIVED` — each machine sends this once its own `UWorld` is the announced map.
- `3 RESUME` — the host releases the pair after both `ARRIVED`, and absolute state may
  be applied again. Until then both machines hold their absolute bodies (the existing
  `MapBoard` divergence gate).
- `4 AREA` — one machine has entered a streamed AREA (a sublevel of the persistent world:
  `780_SZ_Depths`, `760_SZ_AUT`, …). **`map` is still the UWorld and `dest` is the area**:
  the divergence board consumes `map` before the phase is read, so an area name there made
  it compare a world against an area and oscillate (measured: `world: partner=780_SZ_Depths`
  while both machines stood in `Ruins_Level_00`). The receiver
  streams the same area through the game's own level-list mechanism (`FollowHardTravel`
  takes the sublevel path, which never loads the package as a world) and pins it; a name
  it cannot enter is a named `travel: REFUSED the partner's area …` line. This is not
  `HARD_BEGIN`: a hard load of an area is the pawn-less path R102 measured. The sender
  re-announces while pinned, so a reload or a lost datagram heals. Measured failure it
  closes (Session 19's run 3): entering an area was a LOCAL lever on each machine, and one
  600 s run ended with the host in `780_SZ_Depths` and the peer still in the hub.

The host is authoritative on a collision (both machines cross to different maps at the
same instant): the host's `HARD_BEGIN` wins and the peer re-follows once. A hard
transition is not gated on `StreamUnion`; travel coordination has its own switch
(`TravelSync`) so it works with the streaming union disabled.

Two things about this lane are deliberately **not** on the wire, because they were
measured rather than assumed (`LIVE-TEST-LOG` Session 12):

- **No spawn field.** `LoadMapWithLoadingScreen` takes exactly two parameters (`Map:
  NameProperty`, `MapPackage: StrProperty`); its exec thunk marshals those two into the
  body, which only sets `bLoadingMap`, records `CurrentlyLoadingMapPackage` and starts the
  async load. No cooked package names it, and the only native caller of the body is its own
  thunk — so the game never performs this load and there is no leader-side spawn parameter
  to carry. A world without a `PlayerStart` therefore spawns the player at the origin, and
  the spawn point for the hard maps is CONTENT in the destination world (one
  `PlayerTeleportTargetPos` in `900_SipehaWorld`, one `B33smentTeleportPoint` in
  `990_B33sment`). Each machine resolves that marker locally from the world it just loaded,
  or stands beside the partner's streamed position — both machines hold the same world, so
  neither needs to be told. See `qd::travel::ArrivalBoard`.
- **A refusal, not a datagram.** A hard load of the map a machine is already in tears down
  the current world and faults the GAME (Session 11 R92: a stack with no `WINMM` frame).
  `FollowHardTravel` refuses it for every caller, so the handshake, the in-world fallback
  and the rig's own lever cannot reach that fault.

### 3.15b `DAMAGE` (0x24)

```
guid guid            the attacking enemy (its spawner's FGuid); all zero for other causes
i32  amount_centi    1/100 of the game's damage unit
u8   flags           bit0 melee, bit1 ranged, bit2 the amount is an estimate
```

Host → peer, and it exists for exactly one case: an enemy the **host** runs (the partner
is too far for its spawner, or ownership is mid-handoff) attacking the partner across the
distance. Damage has to be applied by the machine that owns the pawn, through
`TryApplyDamage` on a `FB_Damageable`; the host has no object for the partner's body, so
it describes the hit and the peer performs it.

`flags` bit2 is not decoration: when the host cannot resolve the attack's real damage
value, it says so, and the peer logs a guessed hit as guessed. An estimate that is
silently presented as measured is how a balance bug becomes a sync bug.

### 3.16 `CUTSCENE` (0x25)

```
u32  seq             bumps on every change; an older state is discarded
u8   slot            0 = host, 1 = peer, 0xFF = free
u8   state           0 = none, 1 = playing, 2 = ended
str  name            short name of the manager / sequence actor, "" when none
```

A cutscene is per-machine Blueprint state: there is no host-side switch that makes the
other machine play one. Both machines publish the manager they are running (on change
and at 1 Hz), so a lost datagram costs a beat. The receiver resolves the same manager in
its own cooked world and calls the game's own cutscene entry
(`FS_PlayerChar.BeginCutsceneWithManager`); if the manager cannot be resolved, it is held
consistently with `FS_GameInstance.EnterCutsceneMode` until the sender reports `ENDED`,
then released with `ExitCutsceneMode`. `ENDED` is sent explicitly rather than inferred,
because the two machines' managers do not finish on the same frame.

### 3.17 `MOVERS` (0x26)

Moving world objects (elevators, platforms, `Activatable` movers). Owner-authoritative
absolute state: the machine that runs the mover publishes its transform, and the other
machine applies it.

```
u32  rev
u16  n               rows in this body (never split across a datagram)
n × { guid id, i32 x, i32 y, i32 z, i16 yaw, i16 pitch, u8 flags }
```

`id` is the stable FNV-1a identity of the placed actor (its object / level / world names),
the same scheme `DIALOGUE` uses; a mover is a placed actor, so both machines compute the
same id without negotiating. Positions are 1/8 cm and angles 1/65536 turn, as `PLAYER`.

`flags` bit0 = moving (the owner moved it this frame), bit1 = owner (the sender is the
authority). A row whose bit1 is clear is a follower's observation and is not applied.
Ownership follows proximity exactly as `ENEMY` does: the nearer player's machine runs the
mover, so the transform the other applies is the one the interacting player sees.

### 3.18 `LOOT` (0x27)

One shared drop set. The game's `UFS_ItemDropSystem::RollItemDrop` is keyed by
`{sourceId, dropIndex}` with **no player dimension**, so a drop is shared by
construction within one machine — but each machine rolls its own, and the two rolls are
not the same item and not the same centimetre. So the identity is the DEATH that caused
the drop (Session 22):

```
u32  rev
u16  n
n × { u32 source_hash, i32 drop_index, u8 taken, u8 flags, i16 yaw,
      i32 px, i32 py, i32 pz, str item_path }
```

`source_hash` is a mixed hash of the GUID of the enemy that died; `drop_index` is the
ordinal of this drop within that death, in spawn order. Both machines run the same death
for the same GUID, so both compute the same pair without negotiating. `item_path` is the
soft object path the roll produced, never a pointer. `taken` is a tombstone and **wins over
any non-taken entry**: a drop one player picked up must disappear for the other, and a
tombstone is never removed by a later body from the sender that still lists the item.

`flags` bit 0 (`LF_SPAWN`, value 1) says the entry carries a point: `px`/`py`/`pz` are
`QuantizePos` units and `yaw` is `QuantizeAngle`. A receiver that holds no copy of that key
constructs the item class at that point under that key; a receiver that already holds one
builds nothing, so one death yields exactly one drop per machine. A tombstone carries no
point, because there is nothing left to build.

A peer's own rolls are sent as proposals and merged into the host's set; the host's body
is the resolution. The body is absolute and re-sent at 1 Hz, so a lost datagram repairs
itself. `n = 0` is a genuinely empty set.

### 3.19 `SUSPEND` (0x28)

The game writes a timed suspend save on its own schedule (measured: 120 s apart,
alternating slots), gated by `BlockSuspendSaves`. In a live session the peer holds that
gate so its save cannot advance past the host, and a suspend load it does take is
announced so the host can re-apply its absolute state.

```
u32  seq
u8   state           0 = clear, 1 = hold, 2 = loaded, 3 = re-applied
str  slot            the suspend slot name when known, "" otherwise
```

`HOLD` is sent by the peer once it has called the game's own `BlockSuspendSaves`, and
re-sent at 1 Hz as a heartbeat. `LOADED` means the peer took a suspend load anyway (the
gate is not a lock). On `LOADED` the host re-applies `WORLD_FLAGS`, `ACTOR_STATES` and
`INVENTORY` immediately rather than waiting for the 1 Hz cycle, then sends `REAPPLIED`.
`CLEAR` releases the hold when the session ends.

### 3.20 `OBJECTS` (0x2A)

The lane for interactables that are **not** `SavableActorStates` entries. Measured live
(Session 8 R67): `SG_Chest_BP2 [SG_Chest_BP_C] savable=no guid=- index=-1 ... opened=0`.
That chest has no GUID and no container entry, so 3.7 cannot carry it; its state is its
own `Opened` bool. The same is true of a lever/switch (`Activatable`), a placed item
pickup and a gate.

```
u32   rev            bumps once per fully sent body
u16   n              the WHOLE set size, not this datagram's share
n ×:
  u32   key[4]       FNV-1a 128 of the placed actor's "<world>/<level>/<name>" path
  u8    shape        0 none, 1 chest, 2 door, 3 pickup, 4 barricade, 5 activatable
  u8    state        0 closed / not activated, 1 open / activated
```

18 bytes per row; `rev + n` is 6 bytes. A datagram carries whole rows or it does not go
out, so a set larger than one body is a **cursor across ticks**, never a fragment.

`key` is the same construction 3.9's placed-enemy identity uses (`qdenemyid.h`'s PLACED
rule) with its own seed, so the same path hashed by the enemy lane, the dialogue lane and
this one yields three unrelated keys. Both machines compute it from the cooked package,
which is what makes it a key rather than a negotiation. A **runtime-spawned** actor is
excluded: its object name carries that machine's object counter.

`shape` is on the wire so the two logs are comparable and so the receiver can log what the
sender thought the object was; the receiver still classifies locally to choose a property
and a function, because only its own class knows what exists.

**Reliable** (`§2`, and `IsReliableKind` on both sides). An interaction is a one-shot
event: a lost body leaves a chest closed on the wrong machine with nothing to notice it.
The absolute set is re-sent on change, on join, after a suspend load, and by a 5 s repair
pass — a peer that missed a body converges without a special case per cause. There is no
1 Hz heartbeat, because that would re-send the whole set reliably every second.

**A peer's own change is `INTENT` kind 9** (3.10): `key[4]`, `shape`, `state`. The host
applies it to its own copy and publishes the echo, which is the `confirmed=1` the peer
logs. The acceptance gate is the actor-state lane's, including R73's rule that
`based_on_rev == 0` means "no baseline yet", not "stale".

**The apply on the partner is one-directional.** It calls the class' visual/restore entry
(`SetToFinalState` for a chest, `SetToOpenState` for a door, hide + no-collision for a
pickup, `RestoreFromSave` otherwise) and then writes the object's own state property. It
**never** calls the interaction verb: `Interact`, `Grant`, `GrantItemsAndActivate`,
`InsertKey`, `CheckRequiredItems`, `OpenDoor`, `CloseDoor` and `Open` are on a refusal
list in `qdobjectstate.h` and are rejected before a call can be built. A `state` of 0 is
therefore recorded in the ledger but not applied — the game's close/deactivate verbs *are*
the interaction path, so mirroring a `0` would run the verb the partner did not run; the
receiver logs `close-ignored`.

The global counters a chest touches (`TotalChestsOpened`) are **not** part of this lane.
They ride `WORLD_FLAGS` (3.6) exactly as they did before, so nothing is counted twice.

### 3.22 `DIALOGUE_VIEW` (0x50)

The **cursor** the talking player's `DialogueManager` is showing, so the partner can put
the same conversation on **its own** game's dialogue widget. `DIALOGUE` (3.11) already says
*who* is talking to *which* NPC; this says *where in the conversation* they are.

| field | bytes | meaning |
|---|---|---|
| `seq` | u32 | increments per state change; a lower value is discarded |
| `npc` | 16 | the NPC actor's stable placed-object id (the same one `DIALOGUE` carries) |
| `slot` | u8 | 0 or 1 while talking, `0xFF` = the conversation ended |
| `flags` | u8 | bit0 options on screen, bit1 a choice was made, bit2 hide the speaker's name |
| `sequence` | u16 | the talker's `CurrentDialogueSequenceIndex` |
| `entry` | u16 | entry index inside that sequence (0 when the build exposes none) |
| `options` | u16 | how many options the talker may pick from (0 = no option list) |
| `chosen` | u16 | the option the talker picked, `0xFFFF` = none yet |
| `asset` | str | the `FS_DialogueData` object's own name, e.g. `Knight_Arjaot_Dialogue_00` |

**The lines do not travel.** They live in the cooked `FS_DialogueData` asset (61 of them),
which both machines loaded from the same package; the asset's *object name* is the identity.
Sending text would mean re-implementing the localisation lookup (`Game.locres`, nine
locales) and would make the two machines disagree on the one thing the game already agrees
on.

**The outcomes do not travel either, and they did not before.** The receiver calls only the
DISPLAY levers — `ShowDialogueWidget`, `ShowDialogueSequenceEntry`, `ShowDialogueOptions`,
`HideDialogueWidget` — and never `StartDialogue`, `RunAction`, `SaveNamedData` or
`DialogueSequenceEnded`. A dialogue's `NamedSaveDataValueChanges` and `ActionToRun` are
gameplay: running them on a second machine is the double-turn-in the `DIALOGUE` lock was
built to prevent. They ride `WORLD_FLAGS` / `INTENT kind 1` exactly as they always did, so
both players' flags agree while only one machine's conversation produced them.

`seq` is per sender and latest-wins (the `CUTSCENE`/`DIALOGUE` rule): a lost datagram costs
a beat, and a sender silent for 5 s is treated as not talking, so a crash cannot leave the
partner's camera hijacked. The receiver remembers the `(slot, seq)` publication it declined
or hid, so the 1 Hz republish does not re-decide it; a genuine next line is a new `seq`.

### 3.24 `RESPAWN_DOWN` (0x54), `RESPAWN_UP` (0x55), `RESPAWN_REST` (0x56)

**A death is per-player, not a world event** (SYNC-DESIGN §2.9, `qdrespawn.h`). In single
player a death opens the Game Over screen — which pauses that machine's world clock — and
its "Continue" reloads the world from the save. In co-op that reload runs under the
survivor too. This lane replaces it: the pose plays, the Game Over dispatch is refused on
the machine that owns the dead player, and after ~3.5 s that player is put back at **its
own last rest point** with a penalised maximum. Nothing here calls a rest, writes an actor
state, clears an enemy record or asks for a level load.

The machine that OWNS a player is the only authority on that player: there is deliberately
no intent for this lane (an intent is a request to the host, and a player's own health is
not the host's to grant).

Bodies (the envelope's `kind` says which one; no body repeats it):

```
RESPAWN_DOWN  deaths u8 | pct u8 | seq u8 | x i32 | y i32 | z i32
RESPAWN_UP    deaths u8 | pct u8 | seq u8 | x i32 | y i32 | z i32 | yaw i16
              | hp u16 | hp_max u16 | name: u16 len + UTF-8
RESPAWN_REST  deaths u8 (=0) | pct u8 (=100) | seq u8 | x i32 | y i32 | z i32
              | name: u16 len + UTF-8
```

* **Positions are the wire's own 1/8 cm integers** (§3.5), the same encoding `PLAYER` uses:
  one encoding for "where a player is" in the whole protocol.
* **`pct` must equal `100 − 10·deaths`, floored at 10** — the penalty ladder
  (90 %, 80 %, … , 10 %). A body where the stack and the percentage disagree, a `REST`
  that carries a stack, or an `UP` with `hp > hp_max` is **refused**, not applied: applying
  it would either heal a penalised player or penalise a rested one.
* **`seq` is a per-lane counter, applied newest-wins** (`SeqGate`): a duplicate `UP` would
  teleport the partner's puppet back to a rest point the player has left, so a repeat is
  dropped, and the comparison is a **signed** byte — 255 → 0 is newer, not 255 steps older.
* **Reliable.** A death and a respawn are events. A lost `UP` is not fatal (the 30 Hz
  `PLAYER` rows carry the new position) but the puppet would slide across the map instead of
  teleporting, and the partner's bar would lag until the next `STATUS`.
* **`name`** is the rest point's `<actor>/<level>` key: the log names the point on both
  machines, and the owner refuses a point from another map (respawning into an unloaded
  level would need exactly the load this lane exists to avoid).

The receiver does two things and nothing else: on `DOWN` it plays the death pose on the
puppet and remembers the stack; on `UP` it **teleports** the puppet (interpolation buffer
reset, one sample, placed in the same frame — no lerp across the map) and updates the
partner's bar. Its own enemies, progress, area and world are not touched.

### 3.26 `KILL_XP` (0x40)

One death paid one player's XP; the other player is paid the same amount. Both machines run a
copy of a death, and the game's award is Blueprint state -- `FS_PlayerChar_C.Player_GiveXP`,
`AddXP`, the `XPGained` delegate -- with **no** native symbol in the image (`exe_names.txt` has
none of them), so whether a given machine's copy pays is not something either machine can
predict. The amount is therefore **measured**, never derived from the enemy's data:

* each machine watches its own player's XP counter across the death;
* the machine whose game paid reports what it actually paid;
* the other machine pays that amount with the game's own `Player_GiveXP`, and **only** when its
  own measurement was zero.

If both copies paid, both report and both reports are ignored: nothing is awarded twice. If
neither paid, nothing crosses and the log says so. An award the game did not make is never
invented, and a machine with no readable XP counter sends and pays nothing at all.

| field | bytes | meaning |
|---|---|---|
| `id` | 16 | the enemy's key -- the identity every other enemy lane uses |
| `seq` | u16 | the death's ordinal for that key (`0` = unknown). A reliable retransmit carries the same value and is not a second award; a respawned kill is a higher one |
| `xp` | u32 | the measured award. `0` is refused by the decoder -- an award of nothing is not an award -- and so is anything over 1 000 000 |

Reliable: an award lost to a dropped datagram is a player who fought for nothing. A record
expires after 3 minutes, and a report for a death this machine holds **no copy** of is paid after
a 3 s grace window -- so an enemy that exists on one machine only still pays both players -- and
is logged as not backed by a local measurement.

### 3.27 `SAVE` (0x41)

"I saved; write your own slot now." The detector is the game's own save **dispatch**
(`SaveFunctions_C.SaveGameToDisk`, `FS_GameInstance_C.GI_SaveGameToDisk`, `Save Game to Disk`),
so a checkpoint rest, the game's own autosave, a menu save and a scripted save all arrive on this
one body without a per-route hook.

**Refused by name, deliberately.** The suspend saves (`WriteSuspendSave`,
`GI_WriteSuspendSaveImmediately`, `SuspendSaveLoop`, `AsyncSuspendSaveFinished`,
`UnsafeDeleteSuspendSavesOnSlot`) belong to §3.19, and another machine's suspend snapshot is
exactly the rollback that lane exists to prevent. The system saves
(`GI_SaveSystemSaveToDisk`, `GI_QueueSystemSave`, `SaveSystemSaveToDisk`,
`QueueSaveSystemSaveToDisk`) are per-machine settings, not progression.

| field | bytes | meaning |
|---|---|---|
| `seq` | u32 | the sender's own save counter; monotone, so a retransmit is one request |
| `role` | u8 | 1 = host, 2 = peer (diagnostics only; `> 2` is refused) |

Reliable. **The receiver does not answer a save with a save.** The write it performs is
bracketed (`BeginOwnSave` / `EndOwnSave` in `qdprogression.h`), and every save dispatch inside
that bracket is recognised as that write's own echo and is not announced -- one logical save
dispatches several of these names, nested, which is why the guard is a bracket and not a count.
A mirrored save is **deferred, not dropped** while a world load, a travel handshake, a menu, the
local player's death or a cutscene is in progress, or while the game is mid-suspend-write; a
deferral that cannot clear in 20 s is logged as a give-up. The write itself is the game's own
`SaveGameToDisk`, and it is accepted only when the save object's own `LastSaveTime` moves.

### Reliable kinds: ack and duplicate suppression

A receiver acks every copy of a reliable kind (`ACK` with the envelope `seq`) and
delivers only the first; it remembers the last 64 reliable seqs and forgets them if a
seq arrives more than 4096 below the highest seen (the sender restarted). Before this
existed, nothing acked: a reliable body was resent until the sender gave up and every
copy was applied (measured: one Fireball spawned six times).

### 3.23 `PLATFORM_RIDE` (0x48)

Where a **rider stands on a moving platform**, in that platform's own axes. The companion
of `MOVERS`: `MOVERS` says where the platform is, this says where the person on it is.

```
u32  ms               the sender's clock (ordering only)
u16  n                rows in this body (never split across a datagram)
n × { guid id, i32 ox, i32 oy, i32 oz, i16 oyaw, u8 flags }
```

31 bytes a row, at most 4 rows. `id` is the platform's stable identity — the same key
`MOVERS` uses, so a receiver resolves **its own copy** of that platform. `ox`/`oy`/`oz` are
the rider's place in the platform's axes (1/8 cm, as `PLAYER`); `oyaw` is the rider's
heading *relative* to the platform (1/65536 turn), so a turning platform carries the facing.

`flags` bit0 = on (the sender's player is on this platform), bit1 = the platform is moving.
A row with bit0 clear means "I stepped off".

**Why the place and not the position.** A rider's "position minus the platform's position"
is *not* steady: measured 50–900 cm from one frame to the next, because the pawn and the
platform are sampled at different moments of the sender's frame. A standing passenger's
place **in the platform's axes** does not change at all while the platform moves. So the
sender does not measure it mid-ride (see `qdplatforms.h` for the exact rule, ported from
dollsMP `docs/sync/36` §9), and the receiver rebuilds the drawn place as
`its own copy of the platform + axes × place`. That is what makes a rider sit still on a
platform that is itself moving.

Latest wins on `ms`: a reordered body cannot put the partner back on a platform they left.

## 4. Lane discipline

- `PLAYER` and `ENEMY` are **unreliable and absolute**. Losing one costs a
  sample; interpolation hides it; the next one repairs it.
- `WORLD_FLAGS` / `ACTOR_STATES` / `INVENTORY` are **unreliable and absolute**.
  They are re-sent on change and at 1 Hz regardless. A peer with no memory at
  all converges within a second.
- `INTENT` is **reliable** and deduplicated by `(slot, seq)`.
- `DIALOGUE` and `LEVEL_UNION` are **unreliable, absolute, per sender** and
  re-sent periodically; a sender that goes quiet goes stale (5 s / 30 s) rather than
  leaving its last state in force.
- `CUTSCENE`, `MOVERS` and `LOOT` are **unreliable and absolute**, re-sent on change and
  at 1 Hz (10 Hz for `MOVERS`); a silent cutscene sender goes stale in 5 s so a crash
  cannot leave the partner's input locked.
- `TRAVEL` and `SUSPEND` are **reliable**: the hard-transition phases and the
  suspend-load repair are events whose loss would leave the pair in different states
  until the 0.5 Hz / 1 Hz heartbeat, and the handshake is short enough that a lost phase
  is a stuck transition.
- `OBJECTS` is **reliable and absolute**. It is re-sent on change, on join, after a
  suspend load, and by a 5 s repair pass — not at 1 Hz, because a reliable re-send every
  second is a retransmission budget spent on nothing. The counterpart intent (kind 9) is
  on `INTENT`, so it inherits the reliable, deduplicated lane.
- Nothing anywhere carries `x += d`. Every effect is a set insertion, an
  absolute assignment, or a transition guarded by a monotonic counter
  (E2). This is the rule that makes a lost or duplicated datagram change
  nothing.

## 5. MTU and timing

- Datagram cap: 1216 B total.
- `PLAYER` 30 Hz default, 60 Hz allowed (measured < 10 KB/s for two players).
- `ENEMY` 20 Hz, 24 rows maximum in flight.
- `ENEMY_DETAIL` ≤ 10 bodies per rolling second across all enemies, and a per-enemy
  minimum interval by relevance (100 ms critical / 400 ms cosmetic near the receiver,
  rising to 500 ms / 2 s at the far band). A cosmetic change beyond 150 m is not sent.
  This is the lane's bound: it is the one that bursts when a fight is busiest, and it
  yields to `INTENT`, `TRAVEL` and `DAMAGE` because those must not.
- `BOSS` is on change only and cheap (20 B), so it is not rate-limited beyond that.
- Render delay 100 ms, extrapolation cap 250 ms — see `qdmotion.h`.

## 6. Open items this document does not settle

Recorded rather than hidden:

- Authentication: the relay is plaintext and unauthenticated in v1. DollsMP
  GAP-28 calls this out as a shipping blocker for internet play. v1 is LAN /
  direct-IP only; the launcher refuses a public relay address unless
  `[Rules] AllowPlaintextInternet=1` is set and prints the warning.
- Congestion control: none. A fixed ladder with hysteresis replaces an
  integrator (12 §4.5.5).
