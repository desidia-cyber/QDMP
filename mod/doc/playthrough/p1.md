### 2b. Check 3 is a real finding, not a harness accident: the first ~3 minutes after a boot disagree

Every one of the 196 lines is inside the settling window, and **every category healed**:

```
7:51:52.980 INFO audit: OK 11 categories, 45 items          <- first pass: the world is still streaming
7:52:11.825 INFO audit: flags healed (12 items; it had been disagreeing)
7:52:11.825 INFO audit: boss healed (3 items; it had been disagreeing)
7:52:23.928 WARN audit: DESYNC movers <whole set> host=12 peer=0 age=3078 -- asking for the item set ...
7:52:32.083 WARN audit: DESYNC movers f4a7bf38c227ff0944f9d5ca71125df3:x host=-154048 peer=-1 age=10515 [absent on the peer]
7:52:35.543 INFO audit: movers healed (28 items; it had been disagreeing)
7:52:38.065 WARN audit: DESYNC enemy f7f6db21cb3989e2ab187b2742f18091 host=1 peer=-1 age=27593 [absent on the peer]
        ... 64 enemy item rows, and `7:52:46.982 WARN audit: enemy has 88 differing items; 64 printed`
7:54:58.258 INFO audit: enemy healed (130 items; it had been disagreeing)
7:55:53.323 INFO audit: OK 11 categories, 207 items          <- settled, and stays OK
```

What the rows say, measured: **64 enemy keys exist on the host as ALIVE and are absent from the
peer's table** at boot (the peer logged the *same* 64 keys — 64 distinct on both — because the
lines are role-mapped, so both machines agree about the disagreement), and **a mover element
(`f4a7bf38…`) is published by the host with no peer sample**. Both heal within 2.5 minutes as the
peer's table is filled (MirrorSpawn) and the union settles. The row cap works exactly as
documented (`88 differing items; 64 printed`).

So the honest reading is: **the instrument is right and the pair is not clean at boot** — it
converges, it does not start clean. For a "perfect sync, no desync" claim that window is worth
knowing about (a pair that boots and immediately checks would see ~3 min of disagreement about
enemies and movers). It is not a session-breaking bug: nothing else failed, no FAULT, no ERR, the
relay was intact, and the steady state is `OK`.

The script's per-step verdict was therefore made **heal-aware** after this run: it now counts a
category as open only when its last event in the window is a DESYNC rather than a heal, and it
prints which categories are still open. `mod/tools/session-audit.ps1` (not mine, not edited) has
two related defects this run exposes: its "no DESYNC at all" check fails on the settling window,
and its "exactly one item" check counts the `audit: DESYNC … <whole set>` summary as an item
(which would fail a correct one-item report).

### 2c. Harness defects found in my own rig (both fixed before the run)

* `-Relay` never bound: PowerShell is case-insensitive, so `$relay = Join-Path …` overwrote the
  parameter. Renamed to `-RelayExe`.
* The stale-lock test used the lock **directory's** mtime, but rewriting `owner.txt` does not
  touch the parent directory on NTFS (measured: `owner.txt` 07:18:57, directory 07:12:09), so a
  healthy session looked stale and could be broken. The age now comes from `owner.txt`.
