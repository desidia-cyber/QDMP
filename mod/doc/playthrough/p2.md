## 4. Rig and mod findings from this part (every one measured, none inferred)

1. **Placing a player on a teleporter is refused by design** — `RigStandBeside` refuses a spot within
   300 cm of any actor whose name matches `teleport`. The unlock is a `RegisterSphere` **begin
   overlap**, so it needs a body that MOVES into the volume. `Send-Key` (a real WM_KEYDOWN/WM_KEYUP
   W hold posted to the game window, after WM_ACTIVATE) walks the pawn in; that is what produced the
   unlock. A future rig step that needs "a player enters volume X" can use the same lever.
2. **The save's unlock identity is the LocationData asset name**, not the placed actor
   (`Aquatic_Teleporter`, not `Teleporter_Aqr`). Anything that greps a set for the actor name will
   report a false failure.
3. **`QDCOOP_GIVE` truncates at 1024 bytes**, and a key item needs the `+` prefix
   (`SaveFunctions_C.AddItemToInventory`) rather than the cheat's `GiveItem`. A 29-path list silently
   produced an empty inventory (`inventory sent rev=1 entries=0`).
4. **`qd.flag` ignores the same instruction twice** — a second read of one flag needs `#<nonce>`.
   Without it a script reads one value and then gets `(no line)` for every later read.
5. **The area-follow announcement arrives BEFORE the host's own engine line** (peer 06:43:48.641 vs
   host 06:43:48.552 in one case, and 2 s EARLIER in another). A verifier must take the peer's log
   mark before writing the host's `qd.level`, or the follow is always "missing".
6. **The peer's log says `NO level list pushed (no level list known for 'X'); flags forced instead
   … engineVisible=0`** for every area it follows into. The flags (loaded/visible) are forced and the
   geometry is drawn (the picture pairs at every step are not black and not flat), but the peer has
   no level list for the area it is standing in. That is a **tooling asymmetry worth a look**: the
   host pushes a list, the follower does not. It did not produce a visible difference in the five
   areas entered in run 4.
7. **The puzzle lane's actor table is capped at 256** while 463 props were inside its 40 m window, so
   it resolved the peer's rows on the host (`applied=43`) but not the host's rows on the peer
   (`applied=0` — different GObject iteration order ⇒ a different 256). Harmless for static decor
   (a received pose equals the local pose), fatal for any future rotating puzzle.
8. **A long session looks "stale"**: the LIVE lock's `owner.txt` is judged by age, and a single write
   at the start of a 30-minute run reads as abandoned (this happened to me at 06:46). Refresh
   `owner.txt` while holding the lock.
