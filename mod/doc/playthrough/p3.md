**The fix this part adds** — `mod/native/src/qdending.h` (rules) + `ending_lane` in `proxy.cpp`

1. the chooser's machine **observes its own game** running an ending entry (`Banish`/`Eat`/

   brought the picture back, so the game's own wake-up is never claimed for the rescue.

## 2. The three defects this part found and fixed

### D1. `BOSS_END` was never published → the choice never crossed
`expanding on P1`. Fixed by `ending_lane::PublishPump` + `Observe` (the chooser's own game running
`Banish`/`Eat`/`Ending1Complete`/`Ending2CutsceneEnded`, or its bank gaining `EndingNComplete`).
The receiver's `OnEnd` now calls `EndingApplyLocal` → `RigCallVerb` with the same verb on its own
copy, instead of only logging. **Built; unit-tested (90 assertions); NOT yet seen live** —
in R1 the peer had no boss copy, so the receiver refused (`kDriveNoCopy`), which is the designed
behaviour and is what a reviewer should expect to see until the peer is in the arena.

### D2. A machine that only HELD the ending kept a stuck cutscene manager for ever → no wake-up
Measured in R1: the peer logged
`cutscene: Ending1CutsceneManager is playing in this world while this machine holds it for the
partner` eight times, then after the partner's ending ended it **started a local copy at
06:59:36.615 that never ended** (180 s timeout), while its own bank had already written
`Ending1Complete`.  Cause: the ending manager is spawned at runtime, so `CutsceneAct` can only
`CV_HOLD`; the held machine's `CurrentCutsceneManager` is never cleared by the content, and
everything downstream of it (the wake) is unreachable.
Fix (two parts, both in `ending_lane`):
* the ending **flag** opens the wake rules (`g_wake.OnEndingEnded`) — the flag is the content's own
  "the ending is over" fact, so a stuck manager can no longer suppress the wake;
* at 8 s the wake stage calls the player's own **`EndManagerCutscene`** (clears
  `CurrentCutsceneManager`) before cancelling the load lock, then runs `PostEndingWakeOnBeach`
  at 9 s (3 retries) and stops the held fade at 25 s.
The log now says which half ran, so the game's own wake-up is never claimed for the rescue.

### D3. The wake-up was starved by the mod's own level forcing
The ending's wake takes a load lock and waits on `FS_WaitForLevelManagement` (proved from the
cooked `FS_PlayerChar` exports, §0 P3). The stream-union lane forces/re-shows levels every 500 ms,
which is a new entry in exactly that queue. Fixed by `EndingLevelDriveAllowed`: while a wake is
pending (20 s) `StreamPump` and `ViewForceNpcLevel` return early. **This is the fix that should let
the GAME's own wake-up finish, and the log distinguishes it (`... (the game's own)`).**

## 4. Coordination hazard (must be fixed before any full-playthrough claim)

While this part was running, three other delegates were running two-instance sessions on the same
machine. `Stop-All` in the shared rig kills **every** `QueensDomain-Win64-Shipping` and `qd-relay`
process on the box, so concurrent sessions kill each other:
* 06:20 I treated the BUILD lock as stale (its `owner.txt` was 25 min old) but `cl.exe` was
  running — the timestamp proxy is unreliable; check for `cl.exe` first.
* 07:15 my **R2** session reached "session established" on both machines, then both processes were
  killed by another delegate's `Stop-All` 11 s later (`INSTANCE DIED`, `FAULT lines: 0` — a kill,
  not a crash).  A run that is killed this way proves nothing and must not be counted.
**Recommendation:** the LIVE lock is not enough while `Stop-All` is global; either the rig must
kill only its own pids, or every delegate must hold the LIVE lock *and* the runner must refuse to
start when the lock is held (it does not check).
