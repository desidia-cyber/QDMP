## 2. The rig

`mod/tools/session_p4.ps1` - self-contained; takes and releases the LIVE lock itself and obeys
the 2026-11-16 strict rule.

* installs the current `mod/native/build/winmm.dll` (hash printed), writes the shipped ini with
  only `RelayHost`/`RelayPort`/`LogLevel=3` changed, seeds a fresh pair from
  `analysis/save-backup-before-live` (seed bank = 11 flags, so every flag this part asserts is
  NEW), launches two off-screen instances through `run-hidden.ps1`, and asserts
  `relay malformed total=0` before any step;
* **strict lock**: launch nothing without `_test/locks/live`; break another owner only when its
  `owner.txt` is >25 min old AND zero `QueensDomain-Win64-Shipping`/`qd-relay` processes run;
  cleanup kills only the pids this script launched; `owner.txt` is refreshed every ~20 s;
* per step: `qd.level` on one machine + the peer's `travel: entered the partner's area ...`;
  the action is driven on the machine the route says (`qd.act near:<actor>!<verb>`,
  `qd.trigger <Name>@<Area>`, `qd.attack`), never by setting the flag;
* every step ends with `qd.audit` on both, a same-moment screenshot pair, and this run's logs are
  archived into `_test/p4run/out/` before another part can rotate them;
* god mode is **never** enabled (the lever latches on first read and even a `0` enables a 400 HP
  floor), so every boss attempt is a real, killable fight.

Run (Windows PowerShell 5.1 - `pwsh` is not installed here):
`powershell -NoProfile -ExecutionPolicy Bypass -File mod\tools\session_p4.ps1 -Part <secrets|prison|swamp|final>`
or `-Part all -Only R35,R44` to pick steps inside one boot.

## 4. Bugs found (with the exact lines)

### BUG-1 - a secret-zone door (`SecretZoneDoor_BP_C`) is carried by NO lane, and `Activate` is not its open path

```
peer 8:02:12.910 INFO dev interact: forced verb Activate on SecretZoneDoor_Blue_BP
                     [SecretZoneDoor_Blue_BP_C] ran=yes state 0 -> 0
peer 8:02:12.931 INFO dev state: SecretZoneDoor_Blue_BP [SecretZoneDoor_Blue_BP_C]
                     savable=no guid=- index=-1 value=-1 isset=? opened=0
                     isOpen=n/a mySaveData=1 guids=1
both 8:03:04   INFO dev props: SecretZoneDoor_Blue_BP Opened=0 DoorClosed=absent
(no `actor-state intent sent` on the peer, no `object intent sent`, and NO
 `object sync: tracking ... SecretZoneDoor_Blue_BP` line on either machine in 95 tracked objects)
```

The class is `Door_Base_C` but the instance has **no GUID entry**, so `ACTOR_STATES` has nothing
to key on; the OBJECT lane never publishes it (the 95 tracked objects are pots and pickups only);
and its real open path is `InsertKey` (its package carries `InsertKey`, a `VisualKeyComponent`
and `OpenDoor`), not `Activate`. Consequence: **a secret-zone door opened by one player is not
seen by the other** - the user's "secret paths perfectly synced" requirement failing on the one
door family that is the entry to every secret zone.

Fix shape (for the owner of `qdobjectstate.h`/`qdinteract.h`): publish a `SavableActor_C`
subclass instance that has **no GUID entry** on the object lane (the skip must be instance-based,
not class-based), so its `Opened` bool crosses and the receiver runs `SetToOpenState(want)`; then
re-run R35 with `qd.cheat GiveAllKeys` + `near:SecretZoneDoor_Blue_BP!InsertKey` to prove the
player path. NOT fixed here: it is not my module, and the confirming experiment needs a live slot.
